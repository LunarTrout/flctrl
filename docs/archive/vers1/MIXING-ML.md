# MIXING-ML — обученные модели для сведения и перцептивной оценки микса

Ресерч-отчёт. Цель: найти то, чего в нашем стеке ещё нет — обученные модели, которые (а) предлагают решения по балансу/обработке, (б) оценивают микс перцептивно, (в) переносят стиль сведения, и всё это **на CPU без CUDA**.

Дата: 2026-11-02. Машина проверки: Windows 11, 8 физ. ядер / 16 потоков, Python 3.14.9, torch 2.15.0+cpu, `torch.set_num_threads(8)`.

## 1. Дифференцируемый микшер / градиентное сведение

### 1.1 Steinmetz et al. 2021 — Differentiable Mixing Console (DMC) ⭐ работает

- **Статья:** «Automatic multitrack mixing with a differentiable mixing console of neural audio effects», ICASSP 2021 — https://arxiv.org/abs/2010.10291
- **Код:** https://github.com/csteinmetz1/automix-toolkit — **Apache-2.0**
- **Веса:** https://huggingface.co/csteinmetz1/automix-toolkit — **Apache-2.0**, лежат открыто: `enst-drums-dmc.ckpt` (150 MB), `enst-drums-mixwaveunet.ckpt` (214 MB), `medleydb-16-dmc.ckpt`, `encoder.ckpt` (49 MB), плюс тестовый мультитрек `drums-test-rock.zip` и `flare-dry-stems.zip`.
- **Архитектура (важно):** общий энкодер на трек (ShortChunkCNN-Res, mel 128, 16 кГц) → эмбеддинг 512 → конкатенация с «контекстом» (среднее по остальным трекам) → общий MLP → параметры на трек. Общий MLP = permutation-equivariant, поэтому число треков произвольно.
- **Что предсказывает released-чекпойнт:** только **gain + pan** (`num_params = 2`). В статье были ещё нейропрокси EQ/компрессора; в открытом репо этого нет. Это не баг, а упрощение — и оно нам на руку: gain/pan дают 80% слышимого баланса.
- **CPU:** измерено — **35–39× RT** на 4 треках. Для 30-трекового проекта оценка 8–12× RT (энкодер линеен по числу треков, остальное дёшево).
- **Что даёт нам:** (1) готовый «холодный старт» фейдеров/панорамы; (2) **шаблон архитектуры** — 12 М параметров, обучается на одном GPU за часы, inference на CPU бесплатный. Это ровно тот класс модели, который мы можем перетренировать на своих данных (MixParams + наши рендеры) под жанр и под 20–40 треков.
- **Ограничение:** обучен на ENST-Drums (4–8 треков, только барабаны) и MedleyDB-16. На гитарах/вокале в общем миксе поведение не гарантировано — нужен fine-tune.

### 1.2 MixWaveUNet / end-to-end варианты (тот же репо)

- `enst-drums-mixwaveunet.ckpt` (214 MB) — предсказывает **звук**, а не ручки.
- **CPU:** оценка 0.3–1× RT (6–8 М параметров, но полная полоса 44.1 кГц, большие свёртки). Проверять смысла мало: выход — аудио, которое нельзя перенести в FL Studio как параметры, и которое «усредняет» микс (известная проблема black-box систем, см. Diff2Mix §2.4).
- **Вывод:** не наш путь. Интересен только как upper bound качества.

### 1.3 Diff-MST — Transformer-контроллер + DMC

- **Статья:** «Diff-MST: Differentiable Mixing Style Transfer», 2024 — https://arxiv.org/abs/2407.08889
- **Код:** https://github.com/sai-soum/Diff-MST — **CC BY-NC-SA 4.0** (non-commercial!)
- **Веса:** **не опубликованы** (в дереве репо нет ни `.ckpt`, ни `.pth`; inference-скрипт ждёт путь к чекпойнту).
- **Что делает:** по референсному миксу и сырым мультитрекам предсказывает на трек gain, EQ, компрессию, панораму. Self-attention → произвольное число треков, общие MLP → консистентность параметров. Не требует разметки источников.
- **CPU:** оценка 3–8× RT (Transformer поверх DMC-энкодера, но на коротких окнах).
- **Что даёт:** концептуально — то, что нам нужно (параметры, не звук; стиль из референса; без лейблов). Практически — **нельзя**: NC-лицензия + нет весов. Читать как дизайн-документ.
- **Прототип в Cubase:** Diff-MST^C — https://arxiv.org/abs/2411.06576. Показательно: Steinberg встроил именно параметрический подход в DAW. Это подтверждает нашу архитектурную ставку.

### 1.4 MEGAMI — генеративная модель эмбеддингов эффектов (Sony, 2025/26)

- **Статья:** https://arxiv.org/abs/2511.08040 (ICASSP 2026), проект: https://sonyresearch.github.io/MEGAMI/
- **Код:** https://github.com/SonyResearch/megami — **CC BY-NC-SA 4.0**
- **Веса:** **нет** (в README — «checkpoints expected», в репо каталога нет).
- **Идея:** смешивание — задача «один ко многим», поэтому авторы учат conditional diffusion в пространстве эмбеддингов эффектов (FxGenerator), затем нейропроцессор эффектов (FxProcessor, black-box TCN) применяет эмбеддинги к аудио. Domain adaptation в CLAP-пространстве позволяет учиться на «мокрых» записях.
- **CPU:** оценка **0.02–0.1× RT** (итерации диффузии × TCN-процессор). Оффлайн-инструмент, не для цикла.
- **Что даёт:** сильный аргумент, что «правильный ответ» — распределение, а не точка. Для нас практически: **сэмплировать 3–5 вариантов баланса** и отбирать по нашим перцептивным метрикам — дешёвая версия той же идеи без диффузии.

### 1.5 Diff2Mix — диффузия + дифференцируемая консоль (2026)

- **Статья:** https://arxiv.org/abs/2608.05442, проект: https://zys711.github.io/Diff2Mix
- **Код:** https://github.com/ZYS711/Diff2Mix — **лицензия не указана** (юридически «все права сохранены»).
- **Что делает:** контроль стиля двумя способами — референсное аудио (общий стиль) и явные параметры дифференцируемой консоли (интерпретируемость + тонкая оптимизация). Ровно наш кейс «хочу как референс, но с редактируемыми ручками».
- **CPU:** оценка 0.02–0.05× RT.
- **Что даёт:** лучшая на сегодня формулировка задачи. Брать идею «diffusion as prior + differentiable console as decoder», не код.

### 1.6 Sequential Stem Blending (2026)

- **Статья:** https://arxiv.org/abs/2608.05506 (Yeh, Chan, Hung, Yang)
- **Код/веса:** не найдено.
- **Идея:** микшировать не параллельно, а последовательно — каждый стем вливается в растущий сабмикс (как делает человек). Latent flow matching, состояние — контекст сабмикса. Обучение — на синтетике из деградаций.
- **Что даёт:** это **правильная модель для инкрементального агента**: наш агент тоже добавляет треки по одному. Если делать свою модель — вот эта постановка, а не «все треки сразу».

### 1.7 Rule-based + ML гибрид (AES 2025, Reiss group) — практически самый полезный текст

- **Статья:** «A Scalable Two-Stage Automatic Mixing System Integrating Machine Learning and Domain Knowledge», AES 159th Convention, Paper 10232 — https://joshreiss.github.io/documents/2025/Shi2025scalable.pdf
- **Код + аудио:** https://doi.org/10.5281/zenodo.17171082
- **Что делает:** стадия 1 — **правиловый** баланс уровней внутри групп (стемов), стадия 2 — Diff-MST-подобный перенос стиля по референсу. Работает на **100+ треках** — впервые для DL-подхода.
- **Ключевая находка (прямо про нашу боль):** **LUFS плохо работает на узкополосных сигналах** — авторы добавляют спектральный центроид и f0 в оценку громкости для intra-group баланса, и это статистически выигрывает у LUFS-базлайна в слепых тестах по жанрам.
- **Что даёт:** (1) подтверждение, что «энергия/LUFS» — неверная метрика для баса/гитары (мы это знали по Tonal Balance; вот рецензируемое подтверждение); (2) архитектура «правила → потом ML», которая на CPU бесплатна и объяснима; (3) готовая формула уточнения громкости через центроид/f0 — можно внедрить в наш `gain_stage` за день.

## 2. Перенос стиля сведения

### 2.1 MIXSTYLE — Music Mixing Style Transfer (Koo et al., 2023) ⭐ работает, веса есть

- **Статья:** https://arxiv.org/abs/2211.02247 (ICASSP 2023)
- **Код:** https://github.com/jhtonyKoo/music_mixing_style_transfer — **MIT**
- **Веса:** Google Drive, ссылки в README: FXencoder (326 MB), MixFXcloner (42 MB). Отдельной лицензии на веса нет — де-факто MIT вместе с репо (указать в атрибуции). On-premise smoke test: https://huggingface.co/spaces/jhtonyKoo/music_mixing_style_transfer
- **Как устроено:** contrastive-энкодер (PANNs-подобный, 12 свёрточных блоков, 81 M) вытаскивает из референса **только информацию об эффектах** (не о содержании); TCN-конвертер (10.5 M, receptive field ≈ 5.2 с, kernel 15, dilation ×2) переносит обработку на входной стем. Работает постемово (Demucs) или на всём миксе. Поддерживает **интерполяцию между двумя референсами** (это, кстати, лучший UX для «чуть теплее, чем референс»).
- **CPU (измерено):** энкодер 29× RT (анализ референса — один раз), конвертер **0.8× RT**. Песня 4 минуты = ~5 минут CPU. Для оффлайн-A/B и для «как бы это звучало с обработкой референса» — приемлемо; для цикла правок — нет.
- **Что даёт нам:** (1) готовый «проигрыватель стиля» для демо и для проверки гипотез; (2) **главное — FXencoder как дифференцируемая метрика стиля**. Эмбеддинг 2048-мерный, считается за 0.17 с, и его можно использовать как **loss** в оптимизации параметров нашей цепочки: «сделай так, чтобы эмбеддинг моего микса совпал с эмбеддингом референса». Это дешёвый способ получить перцептивный style-loss без обучения чего-либо.
- **Ограничение:** обучен на MUSDB18 (4 стема), 44.1 кГц, стерео; на «мокром» входе требует нормализации громкости (авторы сами предупреждают). Не даёт параметров — даёт звук.

### 2.2 Мастер-стиль / референс-матчинг

- **Matchering 2.0** — уже в стеке, напоминаю только для позиционирования: даёт поканальный матчинг громкости/спектра к референсу, но **без перцептивной модели** (RMS + спектр), поэтому низ переоценивает.
- **fadtk (Microsoft)** — см. §4.3: per-song FAD против референсного корпуса. Это «стилевое расстояние» на уровне распределения, не параметров.
- **Perceptual/rules-based альтернатива без обучения:** наш phonometry N'(z) по 240 полосам → сравнение профиля громкости с референсным профилем → целевая функция для EQ. Дешевле и интерпретируемее любого style-transfer, и уже есть в стеке. Style-transfer-модели имеет смысл подключать только там, где нужно *нелинейное* поведение (компрессия, сатурация, пространство).

## 3. Нейросетевые модели эффектов и предсказание параметров обработки

Это направление важнее, чем кажется: **если модель умеет по желаемому звуку выдать параметры плагина — она стыкуется с FL Studio напрямую**, без рендера и без «звук вместо ручек».

### 3.1 DeepAFx / DeepAFx-ST (Martínez-Ramírez, Steinmetz et al.)

- **DeepAFx** (black-box): «Differentiable Signal Processing With Black-Box Audio Effects», ICASSP 2021 — https://arxiv.org/abs/2105.04752
- **DeepAFx-ST** (style transfer): https://arxiv.org/abs/2207.08759
- **Код:** https://github.com/adobe-research/DeepAFx-ST (415★) — **Adobe Research License: noncommercial research only** (проверено в LICENSE). Плюс форк https://github.com/csteinmetz1/DeepAFx-ST-dev.
- **Веса:** официально не опубликованы; на HF есть только сторонние ONNX-конверсии (`nateraw/deepafx-st-*`, лицензия `other`).
- **Как устроено:** дифференцируемая цепочка (EQ → компрессор → дистошн → реверб) + нейросетевой «прокси» для недифференцируемых эффектов; энкодер извлекает стиль из референса, декодер выдаёт параметры. Обучается на dry/wet парах.
- **CPU:** оценка 1–3× RT на 44.1 кГц (несколько последовательных DSP-блоков + небольшие сети). Реально применимо.
- **Что даёт:** самая близкая к нам постановка «стиль референса → **параметры** эффектов». Но лицензия запрещает коммерческое использование, весов нет → **только идеи и архитектура**. Хорошая новость: всё, что нужно, чтобы повторить, лежит в `dasp-pytorch` (Apache-2.0) — см. 3.2.

### 3.2 dasp-pytorch — дифференцируемые эффекты ⭐ брать

- **Код:** https://github.com/csteinmetz1/dasp-pytorch (304★) — **Apache-2.0**, `pip install dasp-pytorch`
- **Что внутри:** параметрический EQ (biquad-каскад), компрессор, дистошн, реверб, стерео-инструменты. Всё батчится, работает на CPU и GPU, градиенты через параметры.
- **CPU:** измерять не нужно — это чистый DSP на torch; на 10 с стерео 44.1 кГц один проход ≈ 0.05–0.2 с. Сотни итераций оптимизации = секунды.
- **Что даёт:** **механизм замыкания цикла**. У нас есть перцептивные метрики (N, N'(z), sharpness, STI) — но нет способа «подкрутить параметры, чтобы метрика улучшилась». dasp даёт именно это: `loss = f(phonometry(render(params)), target)` → градиент → параметры. Это не «обученная модель», но это то, что превращает наши метрики в действия.
- **Проверенный пример из README:** восстановление параметра дистошна (drive) градиентным спуском за 2500 итераций — то есть blind parameter estimation работает.

### 3.3 Neural parametric EQ / differentiable biquads (Nercessian, iZotope)

- **Статья:** «Neural parametric equalizer matching using differentiable biquads», DAFx 2020. Реализация biquad-каскада — в `dasp-pytorch` (`functional.parametric_eq`).
- **Код:** отдельного репо нет; используем dasp.
- **Что даёт:** точное соответствие «наши ползунки EQ в FL Studio» ↔ «дифференцируемая модель». Fruity Parametric EQ 2 — это как раз каскад biquad'ов, так что параметры переносятся 1:1 (с поправкой на Q/тип фильтра).
- **One-shot style transfer для EQ** (Adobe, Bryan et al., ICASSP 2020): https://njb.github.io/research/icassp2020_style_transfer.pdf — предсказание параметров 4-полосного EQ по референсу одной сетью. Без кода, но метод простой и воспроизводимый.

### 3.4 TAPE — обобщённые представления эффектов (2026) ⭐ свежее и по делу

- **Статья:** https://arxiv.org/abs/2610.40759 (Long, Zang, … Cook, TMLR submission)
- **Код/веса:** на момент проверки не найдено (ищем при внедрении).
- **Что делает:** по **обработанному** референсу оценивает всю цепочку обработки: энкодер классифицирует 8 семейств эффектов → эмбеддинг → дифференцируемый DSP-декодер (EQ, компрессор, waveshaping, малый residual net, реверб) выдаёт **редактируемые параметры** за один forward pass и применяет их к другому, необработанному материалу.
- **Результаты (из абстракта):** меньше спектральная ошибка, чем у DeepAFx-ST; в 275× быстрее, чем per-example поиск по цепочке; **C++-реализация с этими весами обрабатывает буферы по 128 сэмплов в 1.8× быстрее реального времени** — то есть модель принципиально real-time-способна.
- **Что даёт:** это лучший на сегодня ответ на вопрос «можно ли по желаемому звуку предсказать параметры обработки» — да, одной сетью, с редактируемым выходом. Если веса откроют — берём как есть; если нет — архитектура (классификатор семейств + DSP-декодер) воспроизводима на dasp.

### 3.5 Black-box / grey-box моделирование эффектов

- **NablAFx:** https://github.com/mcomunita/nablafx — фреймворк дифференцируемого black-box и grey-box моделирования нелинейных эффектов (Comunità, Steinmetz, Reiss). Лицензия — проверить в репо (обычно MIT/Apache).
- **ToneTwisT AFx Dataset:** https://github.com/mcomunita/tonetwist-afx-dataset — dry/wet пары для исследований эффектов. **Это то, чего не хватает для обучения своих моделей эффектов легально.**
- **Что даёт:** если понадобится «клонировать» конкретный плагин из нашей цепочки (например, Fruity Reeverb 2), grey-box модель обучается на dry/wet парах, которые мы можем сгенерировать сами в FL Studio — это легально и не требует чужих весов.

### 3.6 LLM2Fx-Tools (2025) — tool-calling для пост-продакшна

- **Статья:** https://arxiv.org/abs/2512.01559
- **Что делает:** LLM выбирает типы эффектов, их порядок и параметры, с chain-of-thought; датасет LP-Fx с CoT-аннотациями; проверено и в режиме style transfer (по паре dry/processed).
- **Что даёт:** прямое подтверждение нашей архитектуры «LLM как планировщик + инструменты как исполнители». Полезно как ориентир по формату данных (CoT + tool calls), не как модель.

## 4. Обученные перцептивные метрики (валидированные на музыке, а не на речи)

### 4.1 Что реально коррелирует с предпочтением слушателей — эмпирика, а не мнения

**De Man, Reiss et al., AES 138th (2015), «Perceptual Evaluation of Music Mixing Practices»** — https://joshreiss.github.io/documents/2015/DeMan%20Reiss%20-%20AES138.pdf

98 миксов, 10 песен, 13–22 оценки на микс, все миксы приведены к равной громкости. Корреляции с предпочтением:

| Признак | r | p | Смысл |
|---|---|---|---|
| **side/mid ratio** | **−0.32** | .001 | предпочитают **более узкую стереобазу**; но слишком моно тоже плохо (оптимум, не монотонность) |
| **LDR (микродинамика)** | **+0.26** | .01 | при равной громкости предпочитают **больший динамический диапазон** |
| энергия октавы 4 кГц | −0.21 | .04 | меньше 4 кГц — лучше (жёсткость) |
| MFCC4 | +0.21 | .04 | спектральная оболочка информативна |

Это готовый, рецензируемый, **бесплатный** набор метрик, который у нас не реализован. Side/mid и «избыток 4 кГц» — две строки в numpy. LDR — тоже. Внедрять в тот же день.

### 4.2 CDPAM — learned perceptual audio metric (речь!)

- **Статья:** «A Differentiable Perceptual Audio Metric Learned from Just Noticeable Differences», Interspeech 2020 — https://arxiv.org/abs/2001.04460
- **Код:** https://github.com/luan782/CDPAM (**MIT**) + https://github.com/pranaymanocha/PerceptualAudio
- **Веса:** да, в репо (PyTorch), ~несколько десятков МБ.
- **CPU:** оценка 5–15× RT на 16 кГц моно — быстро.
- **Проблема:** обучался на **JND-экспериментах с речью** (speech enhancement / vocoder). Для музыки не валидирован; штрафует артефакты кодека, а не плохой баланс. Ровно та же болезнь, что у NISQA/SQUIM.
- **Вывод:** не внедрять как метрику микса. Может пригодиться как детектор кодек-артефактов при экспорте.

### 4.3 FAD / FAD∞ (fadtk) — распределительная метрика

- **Статья:** Adapting FAD for generative music evaluation — https://arxiv.org/abs/2311.01616 (+ оригинал https://arxiv.org/abs/1812.08466)
- **Код:** https://github.com/microsoft/fadtk (**MIT**), альтернатива https://github.com/gudgud96/frechet-audio-distance (MIT)
- **Что важно из статьи:** FAD имеет **sample-size bias**, сильно зависит от эмбеддинга и от референсного набора; MusicCaps как референс — плохой (там много «low-quality» и не-музыки). Авторы предлагают FAD∞ (экстраполяция к бесконечной выборке) и референсные наборы **FMA-Pop** и **MusCC** (49 MUSDB18 CC + 240 MoisesDB, студийное качество).
- **Что даёт:** **per-song FAD** — рабочий детектор выбросов («этот микс статистически не похож на профессиональные»). Не «оценка качества», а «насколько мы вне распределения».
- **CPU:** оценка 3–10× RT в зависимости от эмбеддинга (VGGish быстрый, MERT/MuQ — медленнее).
- **Ограничение:** распределительная метрика по определению не может сказать «в этом миксе вокал на 2 дБ тише, чем надо». Только «не похоже».

### 4.4 CLAP-score

- **Код:** https://github.com/LAION-AI/CLAP — **CC0-1.0**, веса `lukewys/laion_clap` (CC0).
- **Что меряет:** соответствие аудио текстовому описанию. Для микса почти бесполезен: «хорошо сведённый рок» и «плохо сведённый рок» дадут близкие CLAP-скоры.
- **Где полезен:** как **семантический слой** для агента — «найди в моём миксе, где „muddy“», «сравни с описанием референса». И как компонент FAD-CLAP.
- **CPU:** ~10–20× RT (HTSAT-аудиоэнкодер).

### 4.5 MuQ-Eval — открытая per-sample метрика качества музыки (2026) ⭐

- **Статья:** https://arxiv.org/abs/2603.22677 («Frozen Music Representations Suffice…»)
- **Код:** https://github.com/dgtql/MuQ-Eval — **MIT**
- **Веса:** https://huggingface.co/zhudi2825/MuQ-Eval-A1 — **MIT** (проверено в карточке модели)
- **Что делает:** замороженные признаки **MuQ-310M** + attention pooling + 2-слойный MLP → MOS-подобная оценка (Musical Impression 1–5). Обучено на MusicEval (2748 клипов от 31 TTM-системы, 13 740 экспертных оценок).
- **Качество:** system-level SRCC 0.957, utterance-level SRCC 0.838 против человеческих MOS. Авторы честно пишут: чувствительно к сигнальным артефактам, **нечувствительно к структурным/музыкальным искажениям**.
- **CPU:** оценка 2–5× RT (MuQ-310M — тяжёлый, но один проход на 10-секундное окно).
- **Что даёт:** единственная **открытая** per-sample метрика качества музыки с высокой корреляцией. Как «детектор брака» (клиппинг, артефакты рендера, кривой лимитер) — годится. Как оценка **баланса** — нет: обучена на сгенерированной музыке, а не на миксах.
- **Важно:** это лучший аргумент против наших старых сомнений — MOS-метрики для речи музыку штрафуют неверно, но **музыкальные** MOS-метрики уже существуют и открыты.

### 4.6 Audiobox Aesthetics (Meta) ⭐ измерено, работает

- **Статья:** https://arxiv.org/abs/2502.05139
- **Код:** https://github.com/facebookresearch/audiobox-aesthetics (**CC-BY-4.0**), веса https://huggingface.co/facebook/audiobox-aesthetics (**CC-BY-4.0**), `pip install audiobox-aesthetics`
- **Что выдаёт (4 шкалы 1–10 на 10-секундное окно):** CE (Content Enjoyment), CU (Content Usefulness), PC (Production Complexity), **PQ (Production Quality)**.
- **CPU (измерено):** 6 с аудио → **0.84 с** после прогрева (**7× RT**); первый вызов 1.3 с (загрузка).
- **Замер на нашем миксе** (`live_now.wav`): `CE 3.29, CU 6.51, PC 1.69, PQ 6.83`.
- **Честное ограничение:** по данным MuQ-Eval, корреляция Audiobox Aesthetics с человеческими оценками слабая (r≈0.20). То есть **абсолютные значения не доверять**. Но как **относительный** сигнал (сравнить 5 вариантов нашего микса между собой, отследить регресс после правки) — дёшево и полезно, особенно PC/PQ, которые реагируют на «сырость» продакшна.
- **Что даёт:** бесплатный «второй слушатель» в цикле, который ловит грубые регрессы (перекомпрессия, грязь, потеря низа) без наших метрик.

### 4.7 DeePAQ (Fraunhofer, 2025) — код не найден

- **Статья:** https://arxiv.org/abs/2510.12326. MERT + LoRA + metric learning, weakly-supervised; лучше существующих метрик на кодировании и обобщается на сепарацию.
- **Код/веса:** не опубликованы (проверено, репозитория нет).
- **Вывод:** следить; сейчас невоспроизводимо.

### 4.8 PEASS — перцептивная оценка сепарации (если понадобится)

- **Код:** https://github.com/CVSSP/peass-software (форк MATLAB-оригинала), Python-порт https://github.com/estevE11/pyass
- **Что даёт:** перцептивные метрики качества разделения (OSS/PMS/APS через слуховую модель PEMO-Q) вместо SDR. Ровно то, что отвечает на нашу проблему «SDR гитары 3 дБ бесполезен».
- **CPU:** быстро (это DSP-модель, не сеть).
- **Вывод:** не приоритет, но если будем оценивать качество стемов перцептивно — вот инструмент.

## 6. Символьные/партитурные подходы и правила, проверенные исследованиями

### 6.1 Символьное сведение — ниша почти пустая

Отдельной литературы «symbolic mixing / score-informed balance» практически нет: поиск даёт score following, инструментовку, транскрипцию — но не баланс. Разумный вывод: **символьный слой нужен не как модель, а как входные признаки**:

- **Slakh2100** даёт MIDI на каждый стем → плотность нот, velocity, регистр, число одновременных голосов. Из этого считается «ожидаемая громкость» трека (плотность × velocity), и это **гораздо лучший приор, чем LUFS**, ровно по той же причине, что в §1.7: узкополосный сигнал с редкими нотами и плотный сигнал с той же энергией воспринимаются по-разному.
- **Инструмент/тип трека** (MixParams: `track_instrument_type`, `track_type`) → целевые диапазоны уровней и EQ-движений.
- **Оркестровые исследования баланса** (Pätynen, Lokki, Aalto) — измерения громкости инструментов в зале; полезны как источник приоров для акустических инструментов, но для рока/электроники малоприменимы. Упоминаю, чтобы закрыть пункт: «партитурные правила» существуют в акустике оркестра, не в поп-сведении.

### 6.2 Классические правила, у которых есть рецензируемая база

| Правило | Источник | Что показано |
|---|---|---|
| «Правиловый» автосмесёр на 11 правилах по инструментам (gain/pan/EQ) | De Man & Reiss, AES 135 (2013), «A knowledge-engineered autonomous mixing system»; обзор — https://joshreiss.github.io/documents/2013/De%20Man%20Reiss%20-%20ARP2013.pdf | правила из учебников сведения формализуемы и дают осмысленный микс; автоматический микс участвовал в слепом сравнении наравне с миксами инженеров (AES 138, Fig. 3) |
| Автономное управление фейдерами по перцептивной громкости | Mansbridge, Finn, Reiss, AES 132 (2012), «Implementation and evaluation of autonomous multi-track fader control» | фейдеры ведут по модели громкости, а не по пикам; база для всех последующих auto-gain |
| **LUFS недостаточен для узкополосных источников** | Shi, Xie, Ma, Reiss, AES 159 (2025), Paper 10232 — https://joshreiss.github.io/documents/2025/Shi2025scalable.pdf | добавление спектрального центроида и f0 к оценке громкости выигрывает у LUFS в слепых тестах по жанрам |
| Меньше side-компоненты, больше микродинамики, меньше 4 кГц | De Man et al., AES 138 (2015) | см. таблицу в §4.1 |
| Маскирование важнее уровня | кросс-адаптивная обработка (Verfaille & Zölzer, «Adaptive digital audio effects») — теоретическая база Unmask/Trackspacer/soothe | «сделать место» = динамическое подавление в полосах, где маскируется целевой источник |

## 7. Коммерческие автмикшеры: что за подход и что воспроизводимо легально

Только описание методов, без декомпиляции и без обхода защиты.

| Продукт | Подход (по документации/маркетингу) | Воспроизводимо? |

| **Trackspacer (Wavesfactory)** | 32-полосный sidechain-EQ: «вырезает» из одного трека спектр, занятый другим, в реальном времени. | **Да**, тривиально: 32 полосы, огибающие, вычитание. Дешёвый «Unmask для бедных». |
| **iZotope Ozone (Master Assistant)** | Анализ микса → целевой тон-баланс/динамика → цепочка мастер-обработки; reference matching. | **Да, кроме обученной части**: у нас есть matchering + phonometry; «тональный баланс» Ozone энергетический и низ переоценивает (мы это уже знаем). |
| **LANDR / eMastered / RoEx / CloudBounce** | Стерео-микс → обученная модель предсказывает параметры цепочки (EQ/компрессия/лимитер) под выбранный «стиль»/интенсивность; LANDR заявляет обучение на тысячах мастерингов и умеет reference upload. | **Подход — да, продукт — нет.** Наша замена: matchering (громкость/спектр) + dasp-оптимизация по перцептивной цели + профиль из референса. |

**Общий вывод по коммерции:** почти все «AI»-фичи сводятся к трём механизмам — (1) кросс-адаптивное подавление маскирования, (2) профиль/целевая кривая из корпуса, (3) оптимизация по слуховой модели. Ни один не требует GPU и ни один не защищён патентом в той форме, в которой мы бы его использовали. Обученные корпуса — единственное, чего у нас нет, и их можно заменить собственными рендерами.

## 8. Антирекомендации (чтобы не потратить время)

1. **End-to-end микшеры, выдающие звук** (MixWaveUNet, MEGAMI, Diff2Mix, MIXSTYLE-конвертер как основной инструмент) — на CPU 0.02–0.8× RT, и главное: выход нельзя перенести в FL Studio как ручки. Только для оффлайн-демо.
2. **Речевые MOS/PESQ/STOI как оценка музыки** — подтверждено повторно; из этой семьи берём только STI (уже есть) и PEASS (если нужно качество стемов).
3. **FAD как «метрика качества микса»** — распределительная, sample-size bias, зависит от эмбеддинга. Только как outlier-детектор и только per-song.
4. **CDPAM** — речь, не музыка.
5. **Diff-MST / MEGAMI / Diff2Mix / DeepAFx-ST в продакшн** — NC-лицензии и/или отсутствие весов. Читать, не тащить.
6. **Обучение своих больших моделей «с нуля»** — при 8 ядрах без CUDA это недели. Правильный путь: крошечные модели (5–15 М) на собственных рендерах + градиентная подгонка параметров через dasp.

## 9. Рейтинг: что внедрять первым

Критерии: (а) даёт ли новые *действия* агенту, (б) цена внедрения на CPU, (в) юридическая чистота, (г) проверяемость.

**Почему №1 именно dasp, а не «обучить модель»:** у нас уже есть лучшая часть — перцептивные метрики, которых нет у большинства исследовательских групп. Не хватает только дифференцируемого исполнителя. Обучать модель имеет смысл *после*, когда есть чем измерять её пользу, и когда есть датасет из собственных рендеров.

## 10. Пять главных пунктов для внедрения

1. **`dasp-pytorch` (Apache-2.0) + phonometry-лосс = оптимизатор параметров.** Строим `loss = w1·|N_target − N(render)| + w2·|N'(z) − target(z)| + w3·sharpness + w4·side/mid`, параметры — biquad-полки/пики + gain + порог компрессора; градиентный спуск за 100–300 итераций на CPU. Это превращает библиотеку из «смотрит и говорит» в «смотрит и правит». Проверено, что схема работает: README dasp восстанавливает drive дистошна за 2500 итераций.

2. **Добавить в панель метрик три вещи, валидированные на 98 реальных миксах:** `side/mid ratio` (предпочтение −0.32), `LDR` микродинамика (+0.26), `энергия октавы 4 кГц` (−0.21), плюс поправку к громкости через спектральный центроид и f0 для узкополосных источников (AES 2025). Это ловит «широко, но пусто», «зажато» и «жёстко на 4 кГц» — то, чего наши N/sharpness/STI не видят.

3. **MixParams (HF, 114 миксов, 2345 записей с реальными настройками EQ/комп и LUFS по треку) → приоры и эталон.** Регрессия «инструмент + жанр + LUFS → gain/EQ/comp» даёт агенту стартовую точку, а не «среднее по больнице». Плюс это готовый способ проверять наши предложения: «инженеры в этом жанре ставят вокал на −2.5 дБ относительно инструментала, а мы предлагаем −6».

4. **DMC из `automix-toolkit` (Apache-2.0, веса открыты, 35× RT) — как инициализатор и как каркас своей модели.** Сейчас предсказывает только gain/pan (12.4 М параметров), что для старта и нужно. Дальше — fine-tune на собственных рендерах FL Studio (у нас есть полный контроль параметров → датасет генерируется легально и в любом объёме), с добавлением EQ/компрессии через dasp-параметры.

5. **Кросс-адаптивный «Unmask» на N'(z) (240 полос Барка) — самый дешёвый скачок в звуке.** Считаем частичную громкость целевого источника в каждой полосе при наличии маскирующего, режем маскирующее динамически только там и только когда; это принцип Neutron Unmask / Trackspacer / soothe2, и он полностью воспроизводим на нашей слуховой модели без обучения и без GPU.

## Приложение B. Механические детали двух главных внедрений

### B.1 Три метрики из §4.1 — формулы

```python
import numpy as np

def side_mid_db(x):                      # x: (2, N), float
    L, R = x[0], x[1]
    S = (L - R) / 2.0
    M = (L + R) / 2.0
    return 10 * np.log10((np.mean(S**2) + 1e-12) / (np.mean(M**2) + 1e-12))

def octave_share_db(x, sr, f_lo=2800, f_hi=5600):
    """Доля мощности октавы 2.8–5.6 кГц относительно полной (дБ)."""
    from scipy.signal import butter, sosfilt
    sos = butter(6, [f_lo, f_hi], btype="bandpass", fs=sr, output="sos")
    band = sosfilt(sos, x, axis=-1)
    return 10 * np.log10((np.sum(band**2) + 1e-12) / (np.sum(x**2) + 1e-12))
```

Ориентир по De Man 2015: `side_mid_db` около −6…−3 дБ (не −15: полностью моно тоже оценивают низко), `octave_share_db` ниже ≈ −18 дБ, LDR — растущий при равной громкости. Точные пороги надо откалибровать на MED 2.0, а не брать из головы.

### B.2 Цикл оптимизации параметров (dasp-pytorch, Apache-2.0)

Сигнатуры проверены по `dasp_pytorch/functional.py`. Внимание: все функции ждут 3-мерный тензор `(batch, channels, samples)` — в наброске ниже `stems[i]` для краткости показан как `(2, N)`, перед вызовом добавьте batch-размерность (`stems[i] = stems[i].unsqueeze(0)`), а после — уберите.

```python
import torch, dasp_pytorch.functional as F

# параметры, которые хотим подобрать (все — torch.nn.Parameter)
p = {
    "gain_db":   torch.nn.Parameter(torch.zeros(n_tracks)),
    "pan":       torch.nn.Parameter(torch.full((n_tracks,), 0.5)),
    "low_gain":  torch.nn.Parameter(torch.zeros(n_tracks)),
    "band_gain": torch.nn.Parameter(torch.zeros(n_tracks, 4)),
    "band_freq": torch.nn.Parameter(torch.tensor([[120., 400., 1500., 5000.]]).repeat(n_tracks, 1)),
    "band_q":    torch.nn.Parameter(torch.full((n_tracks, 4), 1.0)),
    "thresh_db": torch.nn.Parameter(torch.full((n_tracks,), -18.0)),
    "ratio":     torch.nn.Parameter(torch.full((n_tracks,), 2.0)),
}
opt = torch.optim.Adam(p.values(), lr=0.05)

for step in range(300):
    opt.zero_grad()
    tracks = []
    for i in range(n_tracks):                      # (2, N) на трек
        y = F.parametric_eq(
            stems[i], sr,
            p["low_gain"][i], torch.tensor(120.), torch.tensor(0.7),
            p["band_gain"][i, 0], p["band_freq"][i, 0], p["band_q"][i, 0],
            p["band_gain"][i, 1], p["band_freq"][i, 1], p["band_q"][i, 1],
            p["band_gain"][i, 2], p["band_freq"][i, 2], p["band_q"][i, 2],
            p["band_gain"][i, 3], p["band_freq"][i, 3], p["band_q"][i, 3],
            p["low_gain"][i], torch.tensor(8000.), torch.tensor(0.7))
        y = F.compressor(y, sr, p["thresh_db"][i], p["ratio"][i],
                         torch.tensor(10.), torch.tensor(120.),
                         torch.tensor(6.), torch.tensor(0.))
        y = F.stereo_panner(y, sr, p["pan"][i])
        tracks.append(F.gain(y, sr, p["gain_db"][i]))
    mix = torch.stack(tracks).sum(0)
    loss = perceptual_loss(mix, target)   # N'(z)-профиль + side/mid + 4 кГц + sharpness
    loss.backward(); opt.step()
```

`perceptual_loss` — наша phonometry: сравниваем N'(z) по 240 полосам Барка с целевым профилем (из референса или из приоров), плюс штрафы за отклонение side/mid и доли 4 кГц. Градиент течёт через все параметры, включая частоты и Q.

Важно: `parametric_eq` в dasp — каскад biquad'ов, то есть **1:1 соответствует** Fruity Parametric EQ 2 по типу фильтров; после оптимизации значения переносятся в FL Studio как есть (с поправкой «Q ↔ ширина полосы»).

### B.3 Что делать с аудио, а что — с параметрами

- **Параметры** (gain, pan, EQ, компрессия, send'ы): оптимизируем градиентом через dasp, применяем в FL Studio. Быстро, объяснимо, обратимо.
- **Звук** (реверб-хвосты, сатурация, «характер»): только оффлайн и только через MIXSTYLE/DeepAFx-подобные конвейеры; в FL Studio это не переносится, поэтому использовать как референс для слуха, а не как источник правок.
