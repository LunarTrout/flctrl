Документ описывает всё, что мы обсудили и к чему пришли: как я должен видеть проект
FL Studio целиком, слышать его и управлять им. Не код, а договорённость о том,
что строится и почему именно так.

**Ничего не пишем, пока не поискали, не решили ли это уже другие.**

## 2. Что выяснено про FL (факты, проверенные на vers1.flp)

### 2.1. У FL нет внешнего API

Ни REST, ни OSC, ни SDK. Единственный программный доступ — **MIDI Controller Scripting**:
FL загружает Python-файл из `Settings\Hardware\<папка>\device_<имя>.py` и исполняет его
внутри себя. Внутри доступны модули: `transport`, `mixer`, `channels`, `arrangement`,
`patterns`, `playlist`, `plugins`, `ui`, `general`, `device` — 427+ функций.

Это же подтверждают чужие проекты (Flapi, несколько FL-MCP-серверов). Другого пути нет.

### 2.2. Поэтому есть два канала

| Канал | Что даёт | Слабое место |
|---|---|---|
| **Файл `.flp`** | всё состояние на момент сохранения: микшер, плагины, маршруты, ноты | не живой; обновляется при сохранении |
| **Мост (MIDI-скрипт)** | живое управление: плагины, ручки, транспорт | ломается при смене драйвера, требует F10 → Update MIDI scripts |

**Вывод: основа — файл, мост — дополнение для записи.** Файл не может «отвалиться».

### 2.3. Что и где лежит в `.flp` (разобрано и проверено)

Парсер сходится байт в байт: 8651 событие, поток потребляет весь чанк.

| Событие | Содержимое | Формат |
|---|---|---|
| `0xCB` (203) | имена каналов рэка | UTF-16LE |
| `0xCC` (204) | имена дорожек микшера | UTF-16LE |
| `0xE1` (225) | **громкость, панорама, стерео, EQ, посылы** | записи 12 байт |
| `0xEB` (235) | **маршруты** | байт-флаги, по одному на приёмник |
| `0xEC` (236) | флаги дорожки | 12 байт |
| `0xD4` (212) | привязка плагина | u32 insert, u32 slot |
| `0xD5` (213) | **состояние плагина** | поля 50…57, State = 53 |
| `0xC9` (201) | внутреннее имя плагина | UTF-16LE |
| `0xE0` (224) | **ноты** | записи 24 байта, 4684 шт |
| `156` | темп | u32 (мБПМ) |

Раскладка записи `0xE1` (12 байт):

```
[0..3]  u32 = 0
[4]     id параметра    (1 = громкость, 193 = панорама, 194 = стерео,
                         208/209/210 = EQ усиление, 216/217/218 = частоты,
                         224/225/226 = добротность, 64..191 = уровни посылов)
[5]     0x1F — константа
[6]     НОМЕР ДОРОЖКИ (0…500 — в FL столько инсертов)
[7]     0x70 — константа
[8..11] i32 значение    (громкость: 12800 = 0.0 дБ)
```

### 2.4. Чего в файле пока не разобрано

- **значения внутри VST-состояний** — двоичный формат конкретного плагина;
- **автоматизация** — огибающие и точки (следующая задача).

### 2.5. Плейлист — РАЗОБРАН через PyFLP_v2 (проверено)

`pyflp` версии `stemhub-org/PyFLP_v2` открывает `vers1.flp` и отдаёт аранжировку целиком:

```
треков плейлиста: 500
ВСЕГО КЛИПОВ:      779
элемент клипа:     position, length, offsets(start, end), channel, group,
                   muted, item_flags
пример:            position=1, length=27072, offsets=(137.0, 419.0)
```

`offsets` — **обрезанные края клипа** (с какого по какой сэмпл файла играть).
Именно то, без чего нельзя перенести «хвосты погашены как в FL».

**Вывод: писать свой парсер плейлиста не нужно — берём PyFLP_v2.**

### 2.6. Автоматизация — РАЗОБРАНА через PyFLP_v2 (проверено)

```
каналов: 142
автоматизаций: 4
  Tempo      2 точки  (0.0 → 0.7958)
  Tempo #2   2 точки  (0.0 → 0.8333)
  Tempo #3   2 точки  (0.0 → 0.1667)
  Tempo #4   2 точки  (0.0 → 0.1042)
```

**В проекте всего четыре автоматизации, и все — темп.** Других нет, что совпадает
со словами пользователя. Значит «автоматизация» перестаёт быть белым пятном: она
читается, и её немного.

**Итог: из четырёх белых пятен осталось одно** — значения внутри VST-состояний.

### 2.7. Что покрыто полностью (PyFLP_v2 + свой парсер)

## 4. Архитектура

```
                        ┌──────────────────────────────┐
      .flp  ───────────►│  парсер (один проход, mmap)  │
                        └──────────────┬───────────────┘
                                       │
                        ┌──────────────▼───────────────┐
                        │   дерево состояния (JSON)     │◄──── кэш по хэшу файла
                        └──────────────┬───────────────┘
                                       │
        аудио ──► анализ ──────────────┤
        (рендер/стемы)                 │
                                       ▼
                        ┌──────────────────────────────┐
                        │  fl_picture() / fl_query()   │──► я вижу всё
                        └──────────────┬───────────────┘
                                       │
                        ┌──────────────▼───────────────┐
                        │  мост (MIDI-скрипт)          │──► я меняю всё
                        └──────────────────────────────┘
```

### 4.1. Единое дерево, единая адресация

Всё лежит в одной структуре, к любому узлу — путь:

```
проект/темп
проект/микшер/9                          громкость, панорама, стерео, флаги
проект/микшер/9/eq/3                     частота, усиление, Q
проект/микшер/9/посылы/11                уровень
проект/микшер/9/эффекты/0                плагин, состояние, размер
проект/каналы/3                          инструмент, привязка к дорожке
проект/время/темп                        все изменения
проект/время/секции                      границы по звуку
проект/время/такт/33                     что играет
аудио/рендер/<хэш>/стем/вокал/секция/3   центр, ширина, энергия
аудио/баланс/барабаны                    уровень относительно суммы
аудио/маскировка/бас-бочка               перекрытие
аудио/референс/grima                     дельты к эталону
```

Один адрес — любой запрос любой глубины. Не надо помнить, где что лежит.

### 4.2. Слои

**Слой 1 — статика (из `.flp`)**
дорожки: имя, громкость, панорама, стереоразделение, mute/solo/arm, включение эффектов,
полярность, вход/выход, цвет, все 10 полос EQ, все уровни посылов;
маршруты: полная матрица «кто → в кого → с каким уровнем»;
каналы рэка: имя, плагин, вендор, путь, привязка к дорожке, громкость/панорама/mute;
плагины: слот, вставка, состояние (размер + хэш), привязка;
проект: темп, размер, длина, версия, сборка.

**Слой 2 — время**
карта композиции «кто играет когда» по тактам;
изменения темпа;
автоматизация: какие параметры, какие точки;
секции и их границы;
клипы плейлиста: позиция, длина, края.

**Слой 3 — слух (аудио)**
атрибуция: Demucs (разложение) + PANNs (тип звука) + CLAP (похожесть) → каждой дорожке
роль с уверенностью («баян, левая», 0.91);
баланс: уровень каждого инструмента относительно суммы, в дБ;
тембр: центр спектра, наклон, полосы;
динамика: crest, LUFS, RMS по секциям;
стерео: корреляция, ширина, центр;
маскировка: перекрытие инструментов в ERB-полосах;
событийность: плотность атак, рисунок;
сравнение с референсами: дельты по каждому инструменту, коридор.

### 4.3. Свежесть — часть картины

```
СЛУХ: рендер от 14:08 (352 с). Проект сохранён 02:41 → СЛУХ УСТАРЕЛ.
```

Картина сама сообщает, отстают ли мои «уши» от проекта. Это защита от рассуждений
по старым цифрам.

### 4.4. Сравнение с референсами — отдельный слой, гибкий по запросу

Референс — не «эталонная цифра», а такой же объект, как проект: разложенный на стемы,
размеченный по секциям, с профилем по каждому инструменту. Сравнивать можно **как угодно**:

**По охвату:**

| Режим | Что делает |
|---|---|
| **континуально** | огибающая различия по всей длине, шаг 0.1–1 с: где именно я ухожу от рефа и на сколько |
| **по секции** | сравнение внутри секции: вступление / развитие / кульминация / конец |
| **по точке** | конкретный момент (такт, секунда): срез всех метрик сразу |
| **по инструменту** | бас против баса, гитары против гитар, вокал против вокала |
| **по метрике** | только уровень, только тембр, только ширина, только маскировка |
| **по ансамблю** | весь микс против рефа целиком, без разложения |

**Что сравнивается:**

- **уровень** — дБ относительно суммы стемов (не абсолют, иначе смысла нет);
- **тембр** — центр спектра, наклон, энергия по полосам, форманты вокала;
- **динамика** — crest, LUFS по секциям, разброс;
- **стерео** — корреляция, ширина, положение центра;
- **маскировка** — перекрытие инструментов в ERB-полосах;
- **плотность** — события в секунду, рисунок атак;
- **высота** — диапазон и основной тон (для баса, вокала, баяна).

**Форма ответа** — всегда адресуемая:

```
референс/grima/бас/уровень            −4.9 дБ (у меня −2.9) → дельта +2.0
референс/grima/вокал/центр/секция/2   1101 Гц (у меня 2390) → дельта +1289
референс/wintersun/гитары/ширина      −18% к рефу
референс/континуально/0:00–5:52       медиана +3.5 дБ, 90-й перцентиль 5.6 дБ
```

**Коридор вместо одной цифры.** По каждому параметру считается допустимый диапазон
из нескольких референсов (у нас GRIMA, Wintersun, Finntroll, Windir и корпус) — и
попадание в него важнее, чем совпадение с одним треком. Отдельно показывается, где
я выше коридора и где ниже.

**Референсы — часть того же дерева:** `аудио/референс/<имя>/…`, поэтому `fl_query`
работает и по ним, а `fl_diff` умеет сравнивать «мой микс против рефа» так же, как
«проект до и после правки».

## 5. Интерфейс

```
fl_picture()                  вся картина: статика + маршруты + время + слух + свежесть
fl_picture("mix")             только микшер
fl_picture("time")            только композиция во времени
fl_picture("listen")          только слух
fl_query("микшер/9")          любая ветка, любой глубины
fl_diff(a, b)                 что изменилось между снимками
fl_listen()                   пересчитать слух, если устарел
fl_set(...)                   запись через мост (громкость, панорама, ручки плагина)
```

**Правило:** любая работа над FL начинается с `fl_picture()`. Картина всегда в контексте,
поэтому «забыть, что там есть» невозможно.

## 6. Гарантии

| Требование | Как обеспечено |
|---|---|
| **Ничего не пропущено** | выводятся все элементы, а не запрошенные; счётчики «найдено N / выведено N» |
| **Честность** | блок «ЧЕГО Я НЕ ВИЖУ» внизу каждой картины |
| **Скорость** | один разбор, кэш по размеру+дате файла; повторный запрос — миллисекунды |
| **Не ломается** | основа — файл, а не мост; мост нужен только для записи |
| **Актуальность** | хэш и время файла в шапке каждой картины |
| **Обратимость** | снапшот перед любой записью, откат одной командой |
| **Проверка** | после записи значение читается обратно и сверяется |

## 7. Что уже сделано и что подтвердилось на vers1

### Работает
- парсер `.flp` с самопроверкой (8651 событие, сходимость байт в байт);
- `flstate.py` — первая версия картины: темп, микшер, маршруты, EQ, каналы, плагины;
- **рендер FL из командной строки** без GUI: `FL64.exe /Ewav /R"out" "project.flp"` —
  проверено, 352 секунды;
- захват живого звука (WASAPI loopback) — работал на WDM;
- анализ: Demucs, PANNs, CLAP, PESTO, маскировка, секции, сравнение с референсами;
- `humanize.py` — правка velocity в `.flp` (4684 ноты, все были 120).

### Найдено в проекте
- **все фейдеры стоят на 0.0 дБ**, панорамы по центру, EQ не поднят — микшер не тронут;
- звук держат плагины и громкость клипов, а не ручки;
- **маршруты баянов идут не туда:** баян1L → 12 (гитарная шина), баян1R → 13
  (Scream vocal), баян2R → 20 (DRUM BUS), баян2L → мастер;
- цимбалы (7) → мастер, а не в инструментальную шину;
- все ноты имели velocity 120 — отсюда «машинные» барабаны.

### Не работает
- мост flapi (скрипт не загружается; окно `TPythonForm: Script output` снаружи не читается);
- перенос проекта в другую DAW: позиции точные (сдвиг 0 с, корреляция 0.87), но теряются
  автоматизация, состояние Kontakt и часть уровней — **идентичности нет и быть не может**,
  потому что встроенные плагины FL не существуют как VST.

### Ключевая находка по формату

Запись параметров микшера `0xE1` (12 байт):

```
[0..3] 0 | [4] id | [5] 0x1F | [6] (insert<<6)|slot — ОДИН БАЙТ | [7] 0x70 | [8..11] значение
```

Именно однобайтовое поле `[6]` было причиной долгой путаницы: при чтении как u16
инсерты уезжали в 448-е номера и значения «не находились». Источник формулы —
`dawhubapp/flpdiff`, `docs/fl-format/flp-format-spec.md`.

## 11. Слой слуха: измерение против узнавания

Ресерч закрыл главный дефицит: раньше «слух» был самодельными энергетическими
метриками, которые переоценивают низ. Теперь есть перцептивный движок.

**Движок: `phonometry`** (MIT, чистый Python-wheel, Windows без сборки).
Даёт по ISO 532-1: громкость N (соны) и уровень (фоны), удельную громкость N'(z)
по 240 полосам Барка, N5/N10; резкость DIN 45692 (`din`/`aures`/`bismarck`) в acum;
roughness/tonality/fluctuation по ECMA-418-2; ISO 226; STI/STIPA.
Считается по кадрам → одна модель обслуживает любую гранулярность: точка,
такт, секция, весь трек, стем, непрерывная кривая по длине.
352 с материала — 6.4 с счёта. Проверка точности: 74.2 соны против 76.4
официального стационарного пути (3 %).

**Два подъязыка библиотеки, не смешивать:**

| Подъязык | Что отвечает | Единицы | Сравнимо между треками |
|---|---|---|---|
| `measure()` | сколько, насколько | соны, фоны, acum, доли N′, STOI, корреляция | да |
| `describe()` / `nearest()` | на что похоже | метка инструмента, ближайший фрагмент, кривая близости | нет, только внутри задачи |

Правило: **`measure` решает, `describe` ищет.** Число, попадающее в решение
о звуке, обязано прийти из `measure`.

**Что даёт узнавание (эмбеддинги) и где оно врут:**
сильная сторона — атрибуция неизвестных каналов (так опознан баян левая/правая),
поиск похожего места в референсе, непрерывная кривая близости по секциям,
контроль подмены инструмента. Слабая — уровень, жёсткость, абсолютные дельты:
эмбеддинг этих величин не видит.

## 12. Ограничения, зашитые в архитектуру

1. **Стемы нельзя суммировать.** Σ N′ по стемам = 1.55× микса, потому что
   сепаратор не восстанавливает фазу. Доли стемов валидны, абсолютная сумма — нет.
   API обязан отдавать доли, а не сумму.
2. **Гитарный стем непригоден для выводов о балансе** (SDR 3 дБ у MoisesDB).
   Пометка в ответе обязательна, цифру нельзя отдавать как факт.
3. **MOS-метрики для речи не применять** к музыке: NISQA/DNSMOS/SQUIM/UTMOS
   штрафуют дисторшн и стерео, то есть именно то, что в блэк-метале нужно.
4. **Энергетические анализаторы (Tonal Balance, SPAN, true:balance) переоценивают
   низ** — именно из-за них прошлые решения уводили микс.
5. **BS-RoFormer на CPU — 17× реального времени**: для полного трека непригоден,
   только фрагменты.
6. **Сравнивать только однотипные секции.** Иначе тихая вставка получает высокую
   близость просто из-за малой энергии.

## 13. Что подтверждено на живом проекте

- Вставка плагина **через запись в `.flp` работает**: `FabFilter Pro-L 2` встал
  на инсерт 19 и FL его загрузил. Источник записи для любого установленного
  плагина — его `.fst` из базы плагинов FL (это тот же контейнер FLP).
- Перечитывание проекта обязательно: FL не следит за файлом. `fl_reload.py`
  делает это сам (~30 с), руки не нужны.
- Живая вставка плагина API невозможна: проверены все модули, `REC_*` (только
  параметры загруженных), браузер (застревает), `ui.up/down` (не двигают),
  `ui.keySeq` (в 25.2.5 отсутствует), `selectBrowserMenuItem` (no-op),
  `os.startfile` на `.fst` (FL игнорирует).
- Настоящий код FL — `FLEngine_x64.dll` (55 МБ, Delphi), `FL64.exe` — загрузчик
  на 1.1 МБ. Экспортов три, все дельфийская болванка. Живое создание возможно
  только вызовом внутренней функции по адресу (реверс).
