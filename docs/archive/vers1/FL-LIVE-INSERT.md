## 1. Стенд: как Frida управляет FL

`fl_live_insert.py daemon` делает:

1. `safe_fl.frida_spawn()` — закрывает посторонние экземпляры, стартует `FL64.exe`
   с тестовым проектом **приостановленным**, печатает pid.
2. `Process.attachModuleObserver({onAdded})` — `FLEngine_x64.dll` грузится не сразу,
   `getModuleByName` на старте падает. Ловим базу в момент загрузки (0x74200000 в прогонах).
3. **Вызовы только из главного потока.** В JS ставится хук на `user32!PeekMessageW`;
   задания из очереди выполняются в его `onEnter`, если `GetCurrentThreadId() ==`
   поток главного окна (`FindWindowW("TFruityLoopsMainForm")` +
   `GetWindowThreadProcessId`). Это единственный надёжный способ попасть в UI-поток
   без инжекта в конкретный поток.
4. RPC-операции: `call(rva, args)`, `dump`, `readptr`, `scanptr`, `scanpat`,
   `hook(rva, name, base, depth)`, `evaljs` (произвольный JS — основной инструмент
   разведки), `alloc`.

Протокол демона — одна строка JSON на запрос/ответ, порт 9790 (у `Daemon` внутри
`probe`/`slotmap` — 9795).

Хуки снимают: аргументы (6 регистров), строки по указателям, 40 qword со стека
(`rsp+0x28…`) и бэктрейс до 20–22 кадров с именами модулей. Этого хватает, чтобы
восстановить цепочку и границы функций (границы — по `.pdata`, `fl_re_scan.PE.func_of`).

## 2. INSERT — что выяснено и где обрыв

> **Устарело (см. §9).** Вставка и удаление работают. Раздел оставлен как история поиска:
> функция `0xDC3860`, которую здесь называют `makeEffect`, на самом деле **валидатор**
> (`vtable+0x28`), а настоящий загрузчик — `0xE28E70`. Вывод «функция размещения не найдена»
> неверен, причина провала — неверная модель занятости слота (`+0x64`, а не `+0x80`).

### 2.1 Цепочка создания плагина (снята на загрузке проекта, 12 плагинов)

```
0xDC3860  makeEffect(Self = <объект слота>, 0x4FA424, <typeId>, <n>, ...)
  └ 0xDBE5A0  makePluginObj(...)                    745 Б
      └ 0xE29450  newPluginHelper(...)              193 Б
          └ 0xE28E70  pluginCreate(RCX=params, RDX=путь к DLL, ...)
              └ 0xE268B0  loadWrapper(RCX=путь, RDX=&out, R8=params, R9=0)
                  └ LoadLibraryExW(<плагин>_x64.dll)
                  └ GetProcAddress("CreatePlugInstance")
                  └ <плагин>_x64.dll!CreatePlugInstance(host, params) -> RAX = экземпляр
```

Проверено живьём (не выведено статически):

* **любая** DLL плагина отдаёт `CreatePlugInstance` — не только Fruity Wrapper.
  `Fruity Limiter_x64.dll` экспортирует его по адресу `0x5071ABE0` (RVA 0x2DABE0),
  `Fruity Parametric EQ 2_x64.dll` — аналогично. Поэтому хук на этот экспорт даёт
  создание **любого** плагина, включая нативные.
* `loadWrapper` (0xE268B0) — универсальный загрузчик: 12 вызовов на 12 плагинов,
  `RCX` = путь к DLL, `R8` = объект params, возврат `RAX` = экземпляр
  (для EQ: `0x10AF4FE0`).
* `pluginCreate` (0xE28E70): `RCX` = params, `RDX` = путь; возвращает не объект,
  а статус (во всех прогонах `0xEF9408` — указатель на временный буфер).
* Границы функций по `.pdata`:
  `0xE29450..0xE29511`, `0xDBE5A0..0xDBE889`, `0xDC1740..0xDC1887` (генератор),
  `0xDC3860..0xDC3953` (эффект).

Снятые аргументы `makeEffect` при загрузке:

```
makeEffect(Self=0x8BFD280 (объект слота 0), 0x4FA424, 0x5CC5F4F7, 0x16, 0x7, 0x4F9D00)  ; EQ
makeEffect(Self=0x8BFD440 (слот 1),        0x4FA424, 0x1E27BC25, 0x0E, 0x4FA424, 0x4F9D00) ; Limiter
```

Ключевое: **инсерт/слот в аргументах не передаются** — слот задаётся самим объектом
`Self`. То есть «вставить плагин в слот N» = вызвать `makeEffect` с объектом слота N
и нужным `typeId`.

### 2.2 Что такое объект слота (найдено и проверено)

Сканированием памяти по указателю на живой объект плагина найдена таблица:

```
FLEngine_x64.dll + 0x11842F4        (глобал; на прогоне VA 0x753842F4)
   + slot*8   -> указатель на объект слота
```

Объект слота (0x380 байт на слот, аллоцируются все 10 сразу):

| смещение | содержимое |
|---|---|
| +0x00 | `74FB4960` (FLEngine+0xDB4960, интерфейс хоста) |
| +0x28 | `0x00000000020007D0` (константа) |
| +0x30/+0x38/+0x40 | указатели на подобъекты (есть только у занятого слота) |
| +0x48 | отличается у занятого/пустого |
| +0x50 | указатель на строку имени (`Fruity Parametric EQ 2`) |
| +0x78 | inline ShortString — 4-байтовый id (`HQV`, `\ej`) |
| **+0x80** | **HMODULE плагина; 0 = слот пуст** |
| +0x88 | указатель на состояние экземпляра |
| +0x60/+0x68 | счётчики/флаги (0x24 = 36 параметров у EQ) |

Проверка (команда `slotmap`): на `Drum mix` слоты 0/1 инсерта 1 дают HMODULE
`0x50820000` (EQ) и `0x50440000` (Limiter), слоты 2–9 — `0x0`. Совпадает с тем,
что показывает FL.

**Ограничение:** таблица по `+0x11842F4` верна для инсерта 1. Чтение по формуле
`base + (insert-1)*0x50` для инсертов 2–4 даёт копию первых двух записей и мусор —
значит у остальных инсертов массивы лежат в других местах (нужен объект инсерта,
а не глобал). Это важный минус: «универсальной таблицы по RVA» нет.

### 2.3 Что пробовалось и почему не сработало

1. **Повтор вызова `makeEffect(slotObj, 0x4FA424, typeId, 0x16, 0x7, 0x4F9D00)`**
   на свободном объекте слота 2 (и с добавлением базы модуля к «похожим на RVA»
   аргументам) — оба раза `RPCException: None`, то есть внутри происходит
   access violation; FL при этом жив, таблица не меняется.
   Вывод: аргументов недостаточно — функции нужен валидный дескриптор плагина
   (`typeId` — хеш, по нему движок ищет запись в своей базе; для пустого слота
   у него нет ни пути, ни состояния).
2. **Прямой вызов `CreatePlugInstance`** (по протоколу §3.2) не пробовался на запись
   в слот: он создаёт экземпляр, но не кладёт его ни в какую структуру — это
   подтверждено цепочкой (все три уровня выше занимаются именно укладкой).
3. **`0x9B6BE0` (UI insert)** не вызывался: требует живой объект микшера и
   «текущий выбранный слот» в `[Self+0x7F4]/[Self+0x7FC]`; без UI-триггера
   объект не поймать, а подделывать его — это уже сборка Delphi-объекта с нуля.

### 2.4 Чего не хватает для рабочего INSERT

Нужен **дескриптор плагина** — то, что FL кладёт в `makeEffect` третьим-четвёртым
аргументом, и откуда берётся путь/состояние. Кандидаты для следующего шага:

* снять аргументы `makeEffect` не при загрузке, а при **вставке из браузера**
  (хук уже готов, нужен один UI-триггер — но по правилам задачи UI не трогаем);
* либо найти в движке функцию, которая строит дескриптор из `.fst`
  (`fl_add_plugin.py` умеет собирать такой блок в файле — структура известна:
  события `0xC9/0xD4/0xD5` + терминатор `0x62`);
* либо найти объект инсерта (не глобал) и его метод `SetPlugin`, чтобы получить
  путь от слота к плагину, а не наоборот.

> **Устарело (см. §9).** Удаление — `FLEngine+0xE29570`, замена — она же плюс `0xE28E70`.

Не реализованы, потому что это обратная операция к §2: нужно либо обнулить
`+0x80`/`+0x88` в объекте слота и корректно разрушить экземпляр (вызов деструктора

Пробовать «наугад» опасно: при неверном разрушении FL падает или теряет проект,

Структура для работы уже есть: объект слота и его `+0x80` (HMODULE) / `+0x88`
(состояние). Для REPLACE логично: `makeEffect` на тот же объект слота с другим
`typeId` — если дескриптор будет найден, REPLACE получится почти бесплатно.

## 4. BYPASS — работает

**Способ:** живой API FL `mixer.setPluginMuteState(track, slot, state)` через
контроллер-мост (9787). Это не UI и не файл — вызов идёт в тот же движок, что и
кнопка на слоте.

Проверено на `Drum mix` (инсерт 1, слоты 0 и 1):

```
getPluginMuteState(1,0) = 0     -> setPluginMuteState(1,0,1) -> get = 0
getPluginMuteState(1,1) = 1     -> setPluginMuteState(1,1,1) -> get = 0
```

Семантика третьего аргумента инвертирована относительно ожидаемой: `1` = заглушить,
`0` = вернуть. Обратное включение после `1` через `0` в этом прогоне состояние
не вернуло (`get` остался `0`) — то есть **выключение работает достоверно,
включение обратно нужно проверять отдельно** (вероятно, значение кэшируется до
перерисовки слота).

Флаг в памяти **не изолирован**: чтобы снять diff «до/после», нужен триггер
`setPluginMuteState`, а он доступен только через мост, который на шаблоне
`Drum mix` не поднимается (контроллер-скрипт FLStudioMCP привязан к MIDI-порту,
а он настроен в `small.flp`, где плагинов нет).

Вызов: `fl_live_insert.py bypass 1 0 off` (off = заглушить).
Код возврата 4, если состояние не изменилось.

# 9. Живое удаление и вставка плагина — РАБОТАЕТ

Дата: 2026-11-02 (вечер). Всё проверено на `small_drum.flp`, FL 25.2.5 build 5319.
Предыдущий вывод «INSERT/DELETE невозможны» **опровергнут**: он опирался на неверную
модель объекта слота (см. §9.3) и на вызов не той функции (0xDC3860 — это валидатор,
а не загрузчик).

## 9.1 Короткий ответ

| Операция | Что вызывать | Аргументы |
|---|---|---|
| **DELETE** | `FLEngine+0xE29570` | `RCX` = объект слота |
| **INSERT** | `FLEngine+0xE28E70` | `RCX` = объект слота, `RDX` = указатель на Delphi UnicodeString с полным путём к DLL |
| **REPLACE** | сначала `0xE29570`, затем `0xE28E70` | — |
| **Найти объект слота** | скан памяти по vtable `FLEngine+0xDB4960`, в объекте `+0x160` = insert, `+0x164` = slot | — |

Оба вызова — только из главного (UI) потока (в стенде это делает очередь на
`PeekMessageW`, `maincall`). Оба возвращают статус, а не результат; проверять надо
поля объекта и `plugins.isValid` через мост 9787.

## 9.2 Объект слота: карта полей (0x1C0 байт)

Класс с vtable `FLEngine+0xDB4960` (проверено: у пустого и занятого слота vtable один и тот же).

| смещение | размер | что это |
|---|---|---|
| +0x00 | 8 | vtable = `FLEngine+0xDB4960` |
| +0x30 | 8 | интерфейс плагина (создаёт `pluginCreate`, освобождает `unload`) |
| +0x38 / +0x40 / +0x48 | 8 | подобъекты слота (список параметров, хост-адаптер и т.п.) |
| +0x50 | 8 | **имя слота** — Delphi UnicodeString (`EQ`, `COMP`); у пустого 0 |
| **+0x64** | **4** | **СОСТОЯНИЕ: `-1` = пусто, `2` = загружен.** Единственный признак занятости |
| +0x68 | 4 | число параметров плагина (Limiter 18, EQ 36, Reverb 15) |
| +0x78 | 4 | id плагина (`HQV` и т.п.) — у пустого остаётся мусор от прошлого плагина |
| +0x80 | 4/8 | `HMODULE` загруженной DLL; 0 у пустого |
| +0x88 | 8 | **путь к DLL** — Delphi UnicodeString |
| +0x160 | 4 | **номер инсерта** (1..N; 0 — мастер) |
| +0x164 | 4 | **номер слота** 0..9 |
| +0x168 | 4 | константа `0x00320000` |

Размер объекта — ровно `0x1C0`; внутри блока слоты идут подряд с этим шагом.

## 9.3 Что именно делает слот пустым (и почему прежние правки не работали)

Занятость — это **знак** поля `+0x64`:

* `+0x64 == -1 (0xFFFFFFFF)` → слот пуст, `plugins.isValid` = 0;
* `+0x64 >= 0` → слот занят, `plugins.isValid` = 1 (проверены 0, 1, 2, 3, 4, 0x7FFFFFFF);
* `+0x64 < 0` при любом другом значении (`0x80000000`, `0xFFFFFFFE`) → пуст.

Внутренний валидатор движка (`0xDC3860`, он же `vtable+0x28`) требует **ровно 2**
(`cmp dword [Self+0x64], 2`), поэтому правильное значение для рабочего слота — `2`.

Почему прошлая попытка провалилась: обнулялись `+0x30, +0x38, +0x40, +0x50, +0x78, +0x80`,
а `+0x64` не трогали. Все эти поля — **полезная нагрузка** (интерфейс, имя, модуль, путь),
а не флаг: `isValid` смотрит только на `+0x64`. После обнуления нагрузки слот остался
«занятым», просто с нулевыми указателями — отсюда и `isValid = 1`.

**Опасное состояние:** поставить `+0x64 = 2` слоту без экземпляра плагина нельзя —
FL считает его живым, лезет в `+0x30`/`+0x88` и через некоторое время падает
(проверено: процесс умер примерно через минуту после такой записи). Флаг допустим
только вместе с полностью инициализированным объектом.

## 9.4 Как адресуются слоты (важно: фиксированного шага между инсертами нет)

Старая формула `FE+0x11842F4 + (insert-1)*0x50 + slot*8` верна **только для инсерта 1**:
там лежит массив 10 указателей именно первого инсерта, а дальше в памяти идут чужие данные
(отсюда «копии первых записей и мусор» для инсертов 2–4).

Блоки по 10 объектов аллоцируются **отдельно для каждого инсерта**, и их адреса не
образуют арифметической прогрессии: в одном прогоне инсерты 1–6 шли подряд с шагом
`0x1180`, а блок инсерта 7 оказался совсем в другом месте. Поэтому адресовать слоты
надо сканом:

```
scan 'rw-' на паттерн vtable (FLEngine+0xDB4960)
для каждого попадания: ins = [obj+0x160], slot = [obj+0x164]
карта: "ins:slot" -> адрес объекта
```

Скан находит ~5000 объектов этого класса (он используется не только микшером),
но фильтр `slot <= 9 && ins <= 255` даёт ровно 640 = 64 инсерта × 10 слотов.
В карте бывает 1–2 дубля (старые поколения блоков) — берётся первый, и он совпадает
с тем, что видит API (проверено сверкой состояний и имён по всем занятым слотам).

## 9.5 DELETE — родная функция движка

`FLEngine+0xE29570` (`RCX` = объект слота). Что она делает (дизассемблер, 0xE29570..0xE296E1):

1. проверяет `[Self+0x64] == 2`; если нет — идёт по «мягкой» ветке очистки;
2. снимает объект с глобального списка, вызывает `vtable+0x40`, `vtable+0x20`
   (уничтожение экземпляра плагина), `vtable+0xd0`, `vtable+0x80`;
3. освобождает `+0x48`, `+0x40`, `+0x38`, `+0x30`, обнуляет их;
4. `FreeLibrary([Self+0x80])`, затем `[Self+0x80] = 0`;
5. `[Self+0x64] = -1`, чистка `+0x88`, `+0x90`, `+0x68`, `+0xC8`.

То есть это полное удаление: DLL выгружается, экземпляр уничтожается, поля обнуляются.
Ничего вручную добивать не нужно.

Проверено: `delete 1 1` → `+0x64` стало `0xFFFFFFFF`, `+0x80 = 0`, `+0x50 = 0`,
`isValid(1,1) = 0`, остальные 12 плагинов на месте, FL жив (18 треков).

## 9.6 INSERT — родной загрузчик + строка Delphi

`FLEngine+0xE28E70` (`RCX` = объект слота, `RDX` = путь). Это **не** «создание объекта
плагина» (как считалось раньше), а полная укладка плагина в слот:

1. вызывает `vtable+0x30` у слота (подготовка);
2. проверяет существование файла;
3. `loadWrapper(path, &slot+0x80, slot)` → `LoadLibraryExW` + `GetProcAddress("CreatePlugInstance")`
   + `<плагин>!CreatePlugInstance(host, params)`;
4. проверяет флаги загруженного модуля, при ошибке — `FreeLibrary` и выход;
5. заполняет `+0x30` (интерфейс), `+0x38`, `+0x40`, `+0x88` (путь), `+0x68` (число параметров)
   и в конце `[slot+0x64] = 2` (инструкция `mov dword [rax+0x64], 2` по `0xE28FD8`).

**Строка пути — Delphi UnicodeString.** Заголовок на 12 байт перед указателем:

```
[-12] u16 CodePage = 1200 (UTF-16LE)
[-10] u16 ElemSize = 2
[ -8] u32 RefCnt
[ -4] u32 Length (в символах)
[  0] UTF-16 символы + NUL
```

Указатель передаётся на первые символы. `RefCnt` лучше ставить большим (`0x40000000`),
чтобы FL не освободил чужой буфер.

Ловушка Frida: `Memory.alloc` внутри RPC освобождается после возврата из вызова —
буфер надо держать в `globalThis` (в инструменте это массив `__strs`), иначе к моменту
`pluginCreate` по указателю уже мусор и слот молча остаётся пустым (именно так выглядел
первый неудачный прогон: `ret != 0`, `+0x64` не изменился).

Проверено: `insert 1 1 "Fruity Limiter"` → `+0x64 = 2`, `+0x80 = 0x50440000`,
`+0x68 = 18`, `isValid = 1`, `getPluginName = 'Fruity Limiter'`,
`getParamCount = 18`, параметры читаются (`Gain`, `Limiter ceiling`, …).

## 9.7 Что проверено целиком

1. **Полный цикл на живом FL**: delete → insert → delete → insert, в том числе
   в слот другого инсерта (3:1) и в «дальний» блок (7:2). После каждой операции:
   `isValid` соответствует ожиданию, остальные слоты не тронуты, процесс жив.
2. **Стабильность**: 15 с паузы после вставки — FL жив, параметры читаются.
3. **Сохранение и перезагрузка** (главное доказательство, что вставка настоящая):
   `Ctrl+S` (mtime `18:24:16 → 18:41:16`, размер `68 380 → 68 754`), затем закрытие и
   повторное открытие проекта. В файле появились две записи — `insert=3 slot=1
   Fruity Reeverb 2` и `insert=7 slot=2 Fruity Reeverb 2` (было 12 записей, стало 14
   вместе с генератором FPC). После перезагрузки FL видит **13** плагинов,
   оба вставленных на местах, `getParamCount = 15` у каждого.
4. **Ошибочные пути**: вставка VST-пути (`FabFilter Pro-L 2.dll`) не роняет FL —
   `LoadLibraryExW` проходит, но `CreatePlugInstance` у VST нет, слот остаётся пустым.
   Вставка поверх занятого слота без `replace` отклоняется инструментом.

## 9.8 Ограничения и что осталось

* **VST/VST3 пока не вставляются.** Нужен путь через `Fruity Wrapper_x64.dll`:
  обёртка создаётся пустой, а VST-путь и состояние лежат в её params/state
  (в `.flp` это `internal='Fruity Wrapper'` + `pluginpath` + блок `State`).
  Следующий шаг — снять аргументы `newPluginHelper`/`makePluginObj` при загрузке
  проекта с VST и посмотреть, что именно получает обёртка.
* **Мастер (insert 0)** имеет отдельный блок; слот 0 мастера — объект другого вида
  (`+0x64 = 0`), остальные 9 слотов мастера находятся нормально. В этом шаблоне
  на мастере нет плагинов, поэтому не проверялось.
* **Нет undo-записи**: правки идут мимо командного слоя, `general.undo()` их не откатит.
  Флаг «проект изменён» после вставки тоже не всегда поднимается — сохранение лучше
  делать явно (`Ctrl+S`) и проверять mtime.
* **Задержка API ~1 с**: `plugins.isValid` начинает отражать новое состояние не мгновенно
  (движок обновляет слот на ближайшем тике), поэтому читать статус сразу после вызова
  нельзя — в инструменте пауза 1.2 с.
* Удаление/вставка при **открытом редакторе** этого плагина не проверялись.

# 10. Перезагрузка MIDI-скриптов без диалога (Update MIDI scripts)

Дата: 2026-11-02. Бинарь: `C:\Programs\Fl Studio 2025\FLEngine_x64.dll`,
версия **25.2.5.5319**, 57 367 032 байт, sha256 `919c9e47…`. Всё ниже — статика;
живых прогонов не было (в момент работы FL64.exe PID 5620 была занята рабочим
проектом, трогать её запрещено правилами).

## 10.1 Короткий ответ

| Что | Значение |
|---|---|
| Функция | `procedure RefreshMIDI(full: Byte)` |
| RVA | **`0xC77830`** (FLEngine_x64.dll) |
| Аргументы | один байт в **CL** (`full`), больше ничего; `Self` не нужен |
| Возврат | нет (Delphi `procedure`) |
| Вызов | `{"op":"call","rva":"0xC77830","args":[1]}` на UI-потоке |
| Байт-сигнатура | `55 53 48 83 EC 48 48 8B EC 48 C7 45 20 00 00 00 00 48 89 6D 28 88 4D 60` |

Это тот же путь, который FL выполняет по кнопке **«Refresh device list»** на странице
MIDI Settings: закрыть порты → пере-синхронизировать настройки устройств (включая
`ScriptFolder`) → открыть порты заново → **переподключить скрипты**. Именно
переоткрытие портов пересоздаёт объекты `TMIDIInDevice_Python`, поэтому скрипт
контроллера запускается заново.

Кнопка «Update MIDI scripts» — **не** этот путь: это онлайн-апдейтер, он требует
инстанс формы опций (см. 10.2) и headless не вызывается.

## 10.2 Как нашли (DFM → таблица обработчиков → RVA)

1. **DFM страницы MIDI** лежит в `.rsrc` (RVA `0x38C8A5C`). Там:
   ```
   object UpdateScriptsBtn: TQuickBtn
     Hint    = '|Download new and updated MIDI scripts'
     ThemeID = 'forms.options.midipage.updatescriptsbtn'
     Caption = 'Update MIDI scripts'
     OnClick = UpdateScriptsBtnClick
   object RescanMIDIBtn: TQuickBtn
     Hint    = 'Update the MIDI device list when devices have been added or removed'
     Caption = 'Refresh device list'
     OnClick = RescanMIDIBtnClick
   ```
2. **Таблица «имя обработчика → адрес»** в `.text`: запись переменной длины
   `u16 flags | u64 VA (база 0x400000) | u8 len | имя`. Пример записи для
   `UpdateScriptsBtnClick` по RVA `0xE4D9DF`:
   `20 00 | 50 6F 25 01 00 00 00 00 | 15 | "UpdateScriptsBtnClick"` → VA `0x1256F50`
   → RVA `0xE56F50`.
   Так же получены: `RescanMIDIBtnClick` → `0xE545C0`, `MIDIRefreshTimerTimer` →
   `0xC79440`, `MIDIInScriptExploreMenuClick` → `0xE60200`.
3. **`0xE56F50` (Update MIDI scripts)** — 169 байт: пишет статус
   `'Checking for MIDI script updates...'` (строка @ `0xE57028`), затем зовёт
   виртуальный метод `[global->[+0x40]->vtable+0x50](строка, self+0xF50, byte, 0)`
   и следом `[+0x130](bool)`. `Self` в RCX — форма опций, `+0xF50` — объект
   MIDI-страницы. Рядом живёт класс `TUpdater` (`0xC0A91A`), т.е. это сетевой
   апдейтер скриптов, а не локальный рескан. **Без инстанса формы не вызвать.**
4. **`0xE545C0` (Refresh device list)** — весь обработчик:
   ```
   48 83 EC 28      sub  rsp, 0x28
   B1 01            mov  cl, 1
   E8 2F A8 72 02   call 0x357EDFA  -> jmp 0xC77830
   48 83 C4 28      add  rsp, 0x28
   C3               ret
   ```
   То есть кнопка — обёртка над `RefreshMIDI(1)`.

## 10.3 Что делает `0xC77830` (0x240 байт, 0xC77830–0xC77A70)

| Шаг | Адрес | Что это |
|---|---|---|
| 1 | `0x3F9B60` | `BeginWaitCursor` (часы; `GetCursorInfo`/`GetCursor`/`SetCursor`) — операция синхронная, для UI-потока |
| 2 | `0xC77849` | guard: если байт по `[rip+0x430478] != 0` — сразу `ret` (повторный вход) |
| 3 | `0xCCCE10` | сброс глобальных флагов MIDI |
| 4 | `0xC75220(-1)` | обход списка устройств, закрытие портов (аргумент сравнивается с индексом устройства; при `-1` ни одно не переоткрывается точечно) |
| 5 | `0xC77360` | пере-синхронизация настроек каждого устройства, в т.ч. ключа `'ScriptFolder'` (`0xC77728`) |
| 6 | `0xC75A10` | открытие устройств заново + подключение скриптов: строки `'New MIDI device detected'` (`0xC771AC`), `'... has been detected and connected with script: '` (`0xC771EC`), `'ScriptFolder'` (`0xC7716C`) |
| 7 | `0xE5FFC0`, `0xE60B90`, `0xE62CE0` | обновление списков на странице MIDI |
| 8 | `0xAAEEB0` | только при `full != 0`: перестройка списка входов |
| 9 | `0xAAEF10` | сброс состояния элементов списка |
| 10 | `0x3F9C00` | `EndWaitCursor` (счётчик + восстановление курсора) |

Кто ещё её зовёт (важно для доверия к функции):

* `0xE545C0` — кнопка «Refresh device list», `full = 1`;
* `0xC77B20` — инициализация MIDI при старте FL, `full = 0`;
* `0xA17320` — цикл сообщений хоста FL Studio Remote: по сообщению (тип 9/17)
  вызывает `RefreshMIDI(0)` — то есть сама FL дергает её вне диалога, из «чужого»
  контекста;
* `0xCC4DC0`, `0xE5EC20` — служебные пути.

## 10.4 Аргумент `full`

* `full = 1` — как кнопка «Refresh device list»: полный проход + перестройка списков
  устройств. Рекомендуемый вариант для восстановления контроллера.
* `full = 0` — как при старте FL и из хоста скриптов: порты переоткрываются,
  скрипты переподключаются, но списки устройств не перестраиваются. Мягче.

Функция ничего не возвращает; RAX после вызова — мусор.

## 10.7 Ограничения и следующий шаг

  выключено в настройках), рескан его не включит — тогда нужен путь записи настроек

* Отдельного «перечитать только .py» не искали: `0xC75A10` пересоздаёт объект

  вызовами — не проверено. Если после рескана правки в `device_*.py` не подхватываются,
  следующий кандидат — апдейтер (`0xE56F50`) через инстанс формы.
* Вызывать при остановленном транспорте: закрытие/открытие портов может дать
  щелчок и сбросить «залипшие» ноты.

Всё в этом разделе — **статика** (capstone). Живых прогонов не было: в момент работы
`FL64.exe` PID 5620 была занята рабочим проектом пользователя, трогать её запрещено.
Поэтому аргументы восстановлены по *собственным* вызовам FL из её же командных
обработчиков — это не догадка, а те же значения, что передаёт меню микшера.

## 11.1 Короткий ответ

| Что | Insert | Delete |
|---|---|---|
| RVA | **`0xDA7B30`** | **`0xDA86C0`** |
| Границы (.pdata) | `0xDA7B30..0xDA7F1B` (1003 Б) | `0xDA86C0..0xDA8E26` (1894 Б) |
| Подпись | `procedure InsertMixerTracks(index: Integer; count: Integer; flags: Byte)` | `procedure DeleteMixerTracks(list: PInteger; lastIdx: Integer; flags: Byte)` |
| Аргументы | `ECX` = index, `EDX` = count, `R8B` = flags | `RCX` = `int*`, `EDX` = `n-1`, `R8B` = flags |
| Флаги из меню FL | `0x07` | `0x12` (delete), `0x11` (trim unused) |
| Возврат | RAX (не используется) | RAX (не используется) |
| Байт-сигнатура | `55 41 56 41 55 57 56 53 48 83 EC 58 48 8B EC 89 4D 24 89 55 28` | `55 41 56 41 55 57 56 53 48 81 EC 88 00 00 00 48 8B EC 48 C7 45 58 00 00 00` |

Сырые запросы к демону 9790:

```json
{"op":"trackadd","index":null,"count":1,"flags":7}
{"op":"trackdel","index":10,"flags":18}
```

`index:null` = как в меню FL — вставка на месте **выбранной** дорожки (её индекс движок
берёт из `[0x10A9D28]`). Для «в конец» — `index = count-2`.

## 11.2 Глобалы: где живёт микшер

| Глобал (RVA) | Что это | Разворот |
|---|---|---|
| `0x10A7EB0` | указатель на массив записей дорожек | qword → `&tracks[0]` (RVA `0x1181B5C`, секция `.bss`) |
| шаг записи | **`0x1474`** байт | `idx * 0x51D * 4` (в коде всегда через `imul rcx,0x51D`) |
| `0x10A9850` | **счётчик дорожек** (`N` записей) | qword → dword по `+0` (RVA `0xEF5F0C`) |
| `0x10A9D28` | **индекс выбранной дорожки** | qword → dword по `+0` (RVA `0x1403830`) |
| `0x10A9360` | объект-документ микшера (для undo-описаний) | qword → объект |

Проверка счётчика: `0xDA7B30` в самом начале делает `if (index > 502 - *count) return;`,
`0xDAA5F0` — `if (*count >= 502) return -1; *count++`. Валидатор индекса `0xDAA5C0`:

```
valid(i) = (i == 0x1F5) || (0 <= i <= *count - 2)
```

То есть **допустимые индексы дорожек — `0..N-2`**; запись `N-1` служебная (её тип — `2`,
см. ниже). `0` — мастер.

### Запись дорожки (0x1474 байт)

| Смещение | Содержимое |
|---|---|
| `+0x08` | тип: `0` = Master, `1` = Insert, `2` = Current |
| `+0x0C` | указатель на строку имени (пустая → имя строится на лету) |
| `+0x2D` | служебный байт «дорогой пользуются» (его копирует вставка) |
| `+0x250`, `+0x26C` | `-1` при удалении |
| `+0x2E4` | строка роутинга: 502 записи по 8 байт (флаги — байт `+0x2E8 + i*8`); в delete чистится |
| `+0x1294` | строка имени (inline; чистится при сбросе дорожки) |
| `+0x1324` | 10 указателей на объекты слотов (те самые, у которых `+0x160`/`+0x164`) |
| `+0x1460`, `+0x1468` | два объекта с индексом дорожки в `+8` |

Имя новой дорожки **не надо задавать**: `0xDC2450` = `GetDefaultName(idx, isMaster)`
строит `'Insert %d'` / `'Master'` / `'Current'` по индексу, если поле `+0x0C` пустое.
Строка `'Insert %d'` лежит по RVA `0xDC25A0`, сама функция — `0xDC2450..0xDC2560`.

## 11.3 Как нашли

1. **От строки.** В `_strings_xref.py` по `^Insert` нашлись `'Insert %d'` (`0xDC25A0`) и
   `'insert mixer track(s)'` (`0xDA7F48`, ссылки из `0xDA7B30`), `'insert mixer track from preset'`
   (`0xDAB71C`, из `0xDAB4B0`), `'Delete mixer track'` (`0x688338`), `'DeleteMixerTrack'`
   (`0x688308`), `'Trim unused mixer tracks'` (`0x688380`).
2. **Кто зовёт `0xDA7B30`** (`_callers.py`): `0xD9FF60` (команда «добавить N дорожек»),
   `0xDAB4B0` (вставка дорожки из пресета), `0xB3AA70` (redo/undo), `0xDAB9F0`.
   В обоих «создающих» местах аргументы снимаются буквально:

   ```
   0xDAB524:  mov rax,[0x10A9D28]       ; -> выбранная дорожка
   0xDAB52B:  mov ecx,[rax]             ; ecx = index
   0xDAB52D:  mov edx,1                 ; edx = count
   0xDAB532:  movzx r8,byte [0xDAB762]  ; r8b = 0x07
   0xDAB53A:  call 0xDA7B30
   ```
   `0xD9FF60` делает то же самое, только `edx = eax` (сколько дорожек просят), с проверкой
   `count <= 502 - *count`. Отсюда и порядок аргументов: **`(index, count, flags)`**.
3. **Что внутри `0xDA7B30`** (1003 Б):
   `bounds-check` → описание undo (`b36c20`) → запись в undo-историю (`b3ac60`, это
   `'insert mixer tracks'`) → `0xD805F0(newCount)` (счётчик, с клампом `3..502`) →
   построение перестановки `perm[502]` → `b53d00(1)` → **`0xDA7470(perm, 0)`** →
   `b53d00(0)` (закрыть undo-шаг) → `d83560`, `da09c0`, `d92fd0` (выделение) и
   `c7b360`/`ccefd0`/`af96a0` (перерисовка).
4. **`0xDA7470`** — ядро, `ApplyTrackMap(perm: PInteger; saveMap: Boolean)`: копирует записи
   дорожек по перестановке `track[i] = temp[perm[i]]` (через временный буфер 0x281B78),
   при `saveMap` снимает карту для undo (`b3a970`, строка `'mixer track map'`).
   Именно её зовёт и undo-применение (`0xB3A5D0`), и удаление.
5. **Удаление.** Кандидаты перебирались по тем, кто зовёт `0xD805F0` (единственная функция,
   меняющая счётчик). `0xDAA5F0` оказался «увеличить на 1 и вернуть индекс»,
   `0xDAAD40` — «найти свободную дорожку». Настоящее удаление — **`0xDA86C0`**, у него
   ровно три вызывающих: `0xDA8FA0` (delete), `0xDA9D20` (trim unused), `0xB3AA70` (undo).
   Оба «удаляющих» места передают `(int* list, len-1, flags|0x10)`:

   ```
   0xDAA193: mov rcx,[rbp+0x100]       ; массив индексов
   0xDAA19A: mov rax,[rbp+0x88]        ; длина массива
   0xDAA1A1: lea rdx,[rax-1]           ; EDX = n-1
   0xDAA1A5: movzx r8,byte [0xDAA5BC]  ; 0x11  (trim unused)
   0xDAA1AD: call 0xDA86C0
   ```
   Внутри: описание undo (`'delete'` / `'trim unused'` + `' mixer tracks'`) → `b36c20`,
   `b388a0`, `b38750(...,5)`, `b38750(...,6)` → чистка роутинга между удаляемыми и
   остальными дорожками (`d7fdf0` «есть ли route», `da85e0`, `da8000`, `da8040`, `da67f0`) →
   сжатие `perm` без удаляемых индексов → `da7470(perm, flags & 0x10)` →
   `0xD805F0(*count - n)` → сброс освободившихся записей (`d7ee30` — очистка имени/полей,
   `dc59b0(track,0)`).

## 11.4 Аргументы и флаги

### Insert — `0xDA7B30(index, count, flags)`

| reg | Значение |
|---|---|
| `ECX` | **index** — куда вставить, `1..count-2` (0 = мастер, не трогать) |
| `EDX` | **count** — сколько дорожек, `>= 1`, `count + N <= 502` |
| `R8B` | **flags**: `1` — писать undo-шаг, `2` — обновить выделение/UI, `4` — выставить байт `+0x2D` новым дорожкам; меню FL передаёт `0x07` |

`flags=0x07` обязателен: без бита `1` не будет undo-записи, без `4` новые дорожки не
получат служебный байт «занято» (и `trim unused` потом может их снести).

### Delete — `0xDA86C0(list, lastIdx, flags)`

| reg | Значение |
|---|---|
| `RCX` | указатель на массив `int32` с индексами удаляемых дорожек |
| `EDX` | **`n-1`** — индекс последнего элемента массива, НЕ количество |
| `R8B` | `0x12` — delete; `0x11` — trim unused; `0x02` — delete, но **без undo** (бит `0x10` открывает блок регистрации undo, см. `0xDA874E`) |

Массив должен жить до конца вызова (в инструменте он аллоцируется на UI-потоке и
пинится в `globalThis.__keep`).

## 11.6 Что проверено, а что нет

**Проверено статически (и это надёжно):**

* аргументы сняты с двух независимых командных обработчиков FL (`0xDAB4B0`, `0xD9FF60`);
* `0xDA7B30` действительно меняет счётчик (`0xD805F0`) и применяет перестановку (`0xDA7470`);
* `0xDA86C0` — единственная «удаляющая» точка: чистка роутинга + сжатие + уменьшение
  счётчика + сброс освободившихся записей; её же зовёт undo-применение;
* границы функций по `.pdata`, сигнатуры в §11.1.

**Не проверено живьём (FL была занята):**

1. что `count` растёт ровно на 1 и `mixer.trackCount()` это видит;
2. что новая дорожка появляется в конце списка и получает имя `Insert N`;
3. какой именно индекс даёт «в конец»: `count-2` (по логике валидатора `0xDAA5C0`) —
   первый прогон должен это подтвердить; если дорожка встаёт на одну позицию выше,
   брать `count-1`;
4. что удаление не сносит соседние дорожки (проверять `flstate.tracks()` до/после).

## 11.7 Риски и ограничения

* **Только UI-поток.** Обе функции трогают undo-историю и зовут перерисовку; вызов из
  чужого потока — гарантированная гонка. В стенде это `onMain` (хук `PeekMessageW`).
* **Мастер (0) и служебная запись (`count-1`) не удаляются** — в инструменте стоит
  проверка `1..count-2`; при обходе FL поведёт себя непредсказуемо (в `0xDA86C0` цикл
  чистки роутинга начинается с дорожки 1).
* **Плагины на удаляемой дорожке**: `0xDA86C0` не вызывает `0xE29570` (наш delete плагина)
  и не выгружает DLL — записи просто сжимаются, а освободившиеся сбрасываются. Учитывая,
  что тут же создаётся undo-запись (`b36c20`/`b3ac60`), участь объектов решает
  undo-история. Для библиотеки это значит: удалять дорожку с плагинами можно, но
  **сначала снимать снапшот микшера** (`fl.safe.snapshot`), чтобы был путь назад.
* **Счётчик ≠ `mixer.trackCount()`** наверняка: в массиве есть служебная запись
  (`тип 2`), поэтому `fl_trackCount`, скорее всего, будет на 1 меньше `count`.
  Сверять надо дельту, а не абсолют.
* **Версионная привязка.** RVA — для 25.2.5.5319; для другой сборки искать по
  байт-сигнатурам из §11.1 и по строке `'Insert %d'`.
