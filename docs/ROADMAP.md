# ROADMAP: порядок работ и жёсткие правила

## ЖЁСТКОЕ ПРАВИЛО (не переступать)

**Пока библиотека не реализована полностью, проект `vers1` не трогаем.**
Ни правок, ни «пробных» изменений, ни сохранений в нём.
Только чтение файлов для проверки инструментов — и то по минимуму.

Сюда же относятся: живая панорама по треку, движение гитар между секциями,
разведение дублей, «красивое» стерео, доводка звука до референсов.
Всё это — фаза C, то есть **после** библиотеки.

**После полной реализации библиотеки проект можно крутить-вертеть** — любые
правки, любые эксперименты, в том числе на реальном материале.
Условие одно: библиотека закончена целиком, а не «почти».

## Принцип: никаких хардкодных правил

Любое «надо двигать всем», «всегда шире», «всегда резать 300 Гц» — это
хардкод, и он запрещён. Каждое предложение библиотеки обязано выводиться из
измерения: спектра, перекрытия ролей, разброса по секциям, распределения
корпуса. Если обосновать числом нельзя — предложения нет.

Это же касается и самих правил: они должны уточняться по мере проверки
(«сделал → замерил → стало лучше/хуже»), а не оставаться прибитыми.

## Фаза A. Слух (сейчас)

Цель: система, которая по звуку понимает всё, что измеримо, и говорит, что
крутить — по каждому инструменту, громкости, спектру, частотам.

- [x] 29/28 полос, калибровка, Zwicker
- [x] Частичная громкость по ISO 532-2 (Мур-Гласберг), слышимость A, dN/dB
- [x] Роли инструментов по именам и спектру
- [x] Цели из корпуса: распределения + ансамбль ближайших референсов
- [x] Обратная задача: гейны под микс-уровневую цель (28 полос)
- [x] Аудит по фронтам: динамика, спектр, стерео, шум, атаки, клиппинг
- [ ] Аудит: починить моно-потерю и направления «хуже/лучше», прогнать тест
- [ ] Стерео по полосам (ширина в каждой полосе, а не одна цифра)
- [x] Разборчивость вокала (SII/STOI) и «утопание» в конкретных полосах —
      `speech.py`: полная процедура ANSI S3.5 (18 полос, важности и внутренний
      шум из стандарта), по кадрам и только там, где вокал звучит, с
      калибровкой уровня маскера по мастеру. Оценка относительная: база SII
      референсов в `docs/sii_baseline.json`, иначе шкала речевая и к металлу
      неприменима (наш 0.21 против 0.01–0.32 у референсов).
- [x] Метрики эффектов: IR-пробник (RT60/EDT/C50), THD/IMD, дакинг
- [x] **Стена и провалы** — `wall.py`: дыра ищется относительно медианы самого
      трека по 9 полосам и секциям, толщина — доля времени в коридоре ±6 дБ.
      Реальный микс: толщина 1.00 против жанра, один провал — 12 кГц (8.4 дБ).
- [x] **Панорама как форма движения:** `panplan.py` строит план по секциям из
      измеренной ширины: плотно — к краю своей стороны, разрежено — к центру;
      шаг ограничен, низ не двигается, зеркальность пар сохраняется. Реальные
      стемы: гитары −0.37/−0.52/−0.37 против +0.37/+0.52/+0.37.
- [ ] Применение плана панорамы в FL как автоматизации (`mixer.automateEvent`) —
      нужно окно с тестовым проектом
- [x] Отчёт: один вызов → «где мы хуже референсов и что крутить» (report.py + docs/example-report.md)
- [x] **Правки по секциям из измерений** — `decide.py` + цели из корпуса
      (`snrtargets.py`, `docs/snr_baseline.json`). Около 140 строк: инструмент,
      полоса, участок, наш уровень, цель, величина правки с капом.
- [x] **Проверка плана до записи** — `simulate.py`: правки применяются к стемам
      по областям, микс пересобирается и перемеряется. На реальных стемах:
      бас 0.091 → 0.310 по слышимости (доля 3.5 → 13.1 %), гитары 0.536 → 0.447
      (доля 88.2 → 77.2 %) — то есть именно то, что план и обещал.

## Фаза B. API FL (после слуха)

Цель: всё, что делает человек в FL, доступно коду и в реальном времени.
**Главный критерий: ни одна операция не требует перезагрузки проекта.**
Живой режим (attach к открытой FL) — основной путь; перезагрузка проекта —
крайний случай, а не рабочий приём.

- [ ] Полный обхват: дорожки, шины, маршруты, плагины, параметры, автоматизация
- [ ] Реалтайм: чтение состояния и запись без остановки транспорта, с очередью
- [ ] Создание объектов **без перезагрузки**: каналы, клипы, автоматизация
- [ ] VST живая вставка (обёртка/состояние) — единственный известный разрыв
- [ ] Удобство: один вызов — одно действие, понятные имена, ошибки по-человечески
- [ ] Устойчивость: переподключение, таймауты, восстановление после падений
- [ ] Один канон кода: репозиторий, без копий в рабочей папке

## Фаза C. Проект (только после A и B)

- Правки микса по всем фронтам, доведение до уровня референсов
- **Панорама по всему треку:** разнообразная и живая — движение гитар между
  секциями, разведение дублей, дыхание атмосфер; не статичные роли
- Проверка аудитом после каждого шага, откат при ухудшении
- Сведение и мастеринг, сравнение с коридором

## Как понимать «библиотека закончена»

Критерии, а не ощущение:
1. Все пункты фазы A закрыты, аудит и слух проходят тесты.
2. API фазы B закрыт по чек-листу, тесты на чистом проекте зелёные.
3. Нет известных «заглушек» и мест, где код врёт (как было с Demucs-стемами).
4. `tools/check_duplicates.py` чист, дымовые тесты зелёные.
