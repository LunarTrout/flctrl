Главный вывод: **ни один открытый Python-пакет не считает частичную громкость по стемам.**
Ближайшее — MATLAB-модель `moore1997` в AMT (GPL-3) и C-библиотека `deeuu/loudness` (GPL-3).
В Python единственный источник N′(z) по ISO 532-2 — `phonometry`; частичную громкость
придётся собрать самим (это и есть основной объём работы, ~1 день).

Второй вывод (раздел 4): **жанровой модели баланса по ролям в открытом виде не существует.**
Есть части — распознавание инструментов и лида, перенос стиля сведения (Diff-MST, Koo),
агентные пайплайны (MixAgent), корпусные исследования громкости (Fazenda) — но никто не
собирает «роль → слышимость → распределение по жанру → дБ» с проверкой. Это придётся
строить самим, и это главная работа, а не метрики.

## 1. Зачем это всё (мотивация из уже собранного)

Ранее на наших данных выяснилось (числа — из прошлых прогонов, не новые):

- доля N′(z) и вклад в слышимую громкость расходятся в 4–8 раз: барабаны 12.7 % против 1.6 %,
  бас 11.8 % против 2.7 %, «other» 63.6 % против 93.9 %;
- сумма частичных громкостей даёт 0.64 от `N_mix` — величина не аддитивна, нормировать нельзя;
- SII вокала на референсах 0.000–0.093 (насыщение), STOI 0.208–0.679 (различает);
- нет метрики, которая переводит расхождение в дБ ручки и проверяется повторным замером.

Отсюда требования к находкам: (а) считает вклад источника, (б) даёт цель, (в) переводит
её в дБ, (г) проверяется замером.

## 2. Громкость и частичная громкость

### 2.1 `phonometry` — единственный Python-пакет с ISO 532-2

- **Ссылка:** https://github.com/jmrplens/phonometry · docs: https://docs.jmrp.io/phonometry/
- **Что реализует:** ISO 532-1 (Zwicker), ISO 532-2 (Moore-Glasberg, стационарный),
  ISO 532-3 (time-varying MG), DIN 45692 (резкость), ECMA-418-2 (roughness, tonality,
  fluctuation), плюс комнатная и строительная акустика. В README заявлено 1893 проверки
  соответствия стандартам в CI (523 стандарта, 111 доменов).
- **Лицензия:** MIT. PyPI `phonometry`, актуальная 3.3.0 (4.0 в разработке).
- **Установка:** `uv run --no-project --python 3.13 --with phonometry python ...`
  (нужен Python ≥3.13; в основном процессе MCP его нет — только подпроцессом).
- **Входы:** 29 третьоктавных уровней 25 Гц…16 кГц в дБ SPL
  (`loudness_moore_glasberg_from_third_octave`), либо сигнал + fs (`loudness_moore_glasberg_time`).
- **Выходы:** `N` (сон), `N′(z)` (372 бина по ERB-шкале), `centre_frequencies`,
  `loudness_level` (фоны).
- **Применимость:** ядро расчёта. Частичной громкости в API **нет** — только полная и
  удельная. В 4.0 обещан `speech.sii`, в 3.3.0 его нет (проверено: `hasattr(..., "speech") == False`).
- **Как проверить:** conformance-отчёт пакета; у нас — плоские 29 полос 60 дБ → 40.04 сон;
  время вызова ~20 мс на кадр.

### 2.2 AMT `moore1997` — эталонная реализация модели (MATLAB)

- **Ссылка:** https://amtoolbox.org/amt-1.6.0/doc/models/moore1997_code.php
- **Что реализует:** полную модель Moore-Glasberg-Baer 1997, включая пороги, громкость и
  **частичную громкость**.
- **Лицензия:** AMT — **GPL-3.0** (часть моделей под другими лицензиями).
- **Установка:** MATLAB/Octave, не Python. Для нас — только эталон сверки.
- **Входы:** сигнал + fs, опции (`flow`, `fhigh`, режимы).
- **Применимость:** сверить наш Python-расчёт на 2–3 сигналах; в прод не тащить (GPL + MATLAB).
- **Как проверить:** один и тот же стем через AMT и через наш код; расхождение `N_partial`
  должно быть < 5 %.

### 2.3 `deeuu/loudness` — C-библиотека с Python-обёрткой

- **Ссылка:** https://github.com/deeuu/loudness
- **Что реализует:** модель громкости и **частичной громкости** Гласберга-Мура на C,
  есть `loudness.py` (ctypes). 40 звёзд, последний коммит 2019.
- **Лицензия:** **GPL-3.0**.
- **Установка:** сборка C-части (Makefile) + Python-обёртка; одной строкой в `uv` не ставится.
- **Входы:** WAV/массив + fs, параметры модели.
- **Применимость:** второй эталон и источник формул; для внутреннего инструмента — можно,
  для поставки — нет.
- **Как проверить:** сравнить с AMT `moore1997` и с нашим расчётом на одном сигнале.

### 2.4 MoSQITo — альтернатива phonometry

- **Ссылка:** https://github.com/Eomys/MoSQITo
- **Что реализует:** Zwicker loudness (стационарный и time-varying), sharpness, roughness,
  tonality, psychoacoustic annoyance; эталонные тесты в репозитории.
- **Лицензия:** Apache-2.0. PyPI `mosqito`.
- **Установка:** `pip install mosqito`, но **импорт требует `matplotlib`** (иначе
  `ModuleNotFoundError` в `_noise_reduction.py`); проверено на Python 3.11.
- **Входы:** сигнал + fs.
- **Применимость:** запасной вариант, если phonometry сломается; частичной громкости нет.
- **Как проверить:** `loudness_zwtv` на эталонном сигнале из их тестов.

### 2.5 `sottek-hearing-model` — ECMA-418-2 целиком

- **Ссылка:** https://github.com/mlotinga/sottek-hearing-model
- **Что реализует:** слуховая модель Sottek: громкость, резкость, roughness, tonality,
  fluctuation strength по ECMA-418-2 (4-е издание).
- **Лицензия:** **GPL-3.0**. PyPI `sottek-hearing-model`.
- **Установка:** `pip install sottek-hearing-model`; грузит сигнал в память целиком
  (для длинных файлов — сегментами, есть `parallel_cores`).
- **Входы:** сигнал + fs.
- **Применимость:** альтернативная модель громкости (лучше на транзиентах, чем MG);
  **частичной громкости тоже нет**.
- **Как проверить:** их тесты + сравнение с phonometry на 3–4 сигналах (1–2 сона расхождения — норма).

### 2.6 LISQM — реестр реализаций (не код)

- **Ссылка:** https://github.com/ZhenxianLi/LISQM · сайт: https://zhenxianli.github.io/LISQM/
- **Что реализует:** ничего не считает; каталогизирует 42 проекта по 22 метрикам с указанием
  редакции стандарта, лицензии, валидации и последнего коммита. Данные на 2026-11-01.
- **Лицензия:** код MIT, данные CC BY 4.0.
- **Применимость:** перед выбором библиотеки смотреть сюда, чтобы не взять реализацию старой
  редакции ECMA-418-2 (их было четыре с 2020 года). Важное: в списке **нет** ни одного
  открытого partial-loudness — только полная громкость.
- **Как проверить:** n/a (реестр).

### 2.7 `pyloudnorm` — LUFS (BS.1770)

- **Ссылка:** https://github.com/csteinmetz1/pyloudnorm
- **Что реализует:** интегральная и кратковременная громкость по ITU-R BS.1770-4, true peak.
- **Лицензия:** MIT. PyPI `pyloudnorm`.
- **Входы:** сигнал (n,) или (n, ch) + fs.
- **Применимость:** уже используется в `perceptual.lufs`; нужен для калибровки уровня
  прослушивания и для отчёта «наш vs референс».
- **Как проверить:** синус −20 dBFS 1 кГц → −20 LUFS ±0.1.

**Вывод по разделу:** частичной громкости в открытом Python-коде нет. Собираем сами:
`N_partial = N(mix) − N(mix без стема)` на покадровых 29-полосных спектрах с одной
калибровкой по миксу (75 дБ SPL). Это формула Ward 2012 (раздел 3.1) и эквивалент Stage 3
модели MG при аддитивном возбуждении.

## 3. Атрибуция источников и маскировка (главное)

### 3.1 Ward, Reiss, Athwal (2012) — multi-track mixing via partial loudness

- **Ссылка:** https://joshreiss.github.io/documents/2012/WardReissAthwal-AES133-Multitrackmixingusingamodelofloudnessandpartialloudness.pdf
- **Что реализует:** кросс-адаптивный метод: фон = сумма возбуждений всех остальных стемов,
  цель = частичная громкость каждого стема; фейдеры двигаются так, чтобы частичная громкость
  каждого стема следовала целевой кривой.
- **Лицензия:** статья AES, код не опубликован.
- **Применимость:** прямая основа нашего `attribute.py`; формулы — в приложении B.
- **Как проверить:** на 4 стемах поднять одному +6 дБ — метод должен вернуть +6 ± 0.7 дБ.

### 3.2 Ma, Reiss, Black (2014) — partial loudness in multitrack mixing

- **Ссылка:** https://www.eecs.qmul.ac.uk/~josh/documents/2014/Ma%20Reiss%20Black%20-%20AES53.pdf
- **Что реализует:** частичная громкость как «высокоуровневые перцептивные метаданные»
  многодорожечного микса; как хранить и использовать в semantic audio.
- **Лицензия:** статья.
- **Применимость:** аргументация, почему вклад считается в partial loudness, а не в N′.
- **Как проверить:** n/a (теория).

### 3.3 Ward (2016) — loudness algorithms for automatic mixing

- **Ссылка:** https://www.eecs.qmul.ac.uk/~josh/documents/2016/Ward.pdf
- **Что реализует:** обзор и практические рекомендации по применению моделей громкости
  к авто-миксу (какие метрики, какие ловушки).
- **Лицензия:** препринт/слайды.
- **Применимость:** чек-лист при внедрении (калибровка, временное сглаживание, целевые кривые).
- **Как проверить:** n/a.

### 3.4 MixViz (Ford, Cartwright, Pardo, 2015) — визуализация маскировки

- **Ссылка:** https://interactiveaudiolab.github.io/assets/papers/FordCartwrightPardo_AES2015.pdf
- **Что реализует:** покадровая specific partial loudness каждого стема против суммы
  остальных; визуализация «кто кого перекрывает» по частоте и времени; расширение — учёт
  пространственной развязки (spatial release from masking).
- **Лицензия:** статья; код MixViz — MATLAB.
- **Применимость:** модель для отчёта по областям и для «горячих» участков; подсказывает,
  что панораму надо учитывать отдельным множителем (у нас пока нет).
- **Как проверить:** синтетика: два стема в одной полосе, развести по панораме —
  частичная громкость должна вырасти (в нашей моно-модели — нет).

### 3.5 Hafezi & Reiss (2015) — авто-EQ по снижению маскировки

- **Ссылка:** https://www.academia.edu/31085393/Autonomous_Multitrack_Equalization_Based_on_Masking_Reduction
  (DOI 10.17743/jaes.2015.0021)
- **Что реализует:** упрощённая мера маскировки MUR (masked-to-unmasked ratio), офлайн- и
  real-time авто-EQ, который срезает маскер в полосах перекрытия; слушательский тест —
  система близка к профессиональному миксу при одном пользовательском параметре.
- **Лицензия:** статья; патент и коммерческое применение.
- **Применимость:** алгоритм «разгрузка вместо подъёма» — наш пункт 11.2.4.
- **Как проверить:** пара стемов с известным перекрытием: после среза маскера частичная
  громкость цели растёт, а её тембр не меняется.
- **Оговорка авторов:** существующие объективные меры маскировки (включая MUR) **плохо
  предсказывают воспринимаемую маскировку в музыке** — нужен слушательский тест или
  проверка на корпусе.

### 3.6 Frontiers 2018 — обзор кросс-адаптивных эффектов

- **Ссылка:** https://www.frontiersin.org/journals/digital-humanities/articles/10.3389/fdigh.2018.00017/full
- **Что реализует:** систематический обзор кросс-адаптивных эффектов (auto-adaptive,
  external-adaptive, cross-adaptive), таксономия и примеры (Dugan automixer → авто-микс).
- **Лицензия:** CC BY.
- **Применимость:** словарь и рамка для описания наших правил; подтверждает, что
  «side-chain + анализ нескольких сигналов» — признанный класс.
- **Как проверить:** n/a.

## 4. Жанровая модель баланса

Это главный раздел: не «набор метрик», а переносимый на любой проект конвейер
**роли → слышимость → распределение по жанру → ближайшая точка → дБ → проверка**.
Литература закрывает куски, но не весь конвейер; где не закрывает — сказано прямо.

```
треки проекта
   │  roles.py: имя + эмбеддинг + активность  →  роль (kick/snare/hats, bass,
   │                                              gtr_rhythm, gtr_lead, keys, vocals)
   ▼
шины ролей (несколько стемов на роль)
   │  partial.py: N_partial(роль) = N(микс) − N(микс без роли); A = N_p / N_solo
   ▼
вектор A_role(7 областей) + активность + плотность
   │  genre.py: распределение по жанру (медиана + ковариация), расстояние Махаланобиса
   ▼
«роль X: +2.5 дБ в pres»  →  apply  →  перемер  →  verify (замкнутый цикл)
```

### 4.1 Роли вместо стемов

Проблема: 4-стемовая таксономия Demucs сваливает гитары, баян и атмосферы в `other`,
а роли в миксе — это не стемы: «барабаны» = бочка + малый + железо + румы, «гитары» =
ритм + лид, и т.д. Нужен слой, который переводит дорожки проекта в **роли**.

| метод | ссылка | что даёт | лицензия | как проверить |
|---|---|---|---|---|
| **OpenMIC-2018** — multi-instrument activity detection | https://github.com/cosmir/openmic-2018 · https://zenodo.org/records/1492445 | покадровая вероятность активности 20 инструментов; обучено на крауд-метках, робастно к слабой разметке | CC BY 4.0 | на 30–50 вручную размеченных дорожках — confusion matrix; цель: ≥80 % по макро-F1 для 6–8 ролей |
| **IRMAS** — instrument recognition | https://www.upf.edu/web/mtg/irmas | 11 классов инструментов, полифонические треки | research-only (по запросу) | как второй голос: расхождение с OpenMIC на одной дорожке — сигнал неопределённости |
| **MedleyDB instrument activations** | https://medleydb.weebly.com/ · paper: https://www.justinsalamon.com/uploads/4/3/9/4/4394963/bittner_medleydb_ismir2014.pdf | истинная разметка инструментов по времени на реальных многодорожечных записях | CC BY-NC-SA 4.0 (некоммерч.) | использовать как валидацию, не как обучение, если проект коммерческий |
| **Lead Instrument Detection** (Ou, Takahashi, Wang, 2025) | https://arxiv.org/html/2503.03232 | определяет **лид-инструмент** по трекам: track-wise attention, self-supervised, робастно к невиданным инструментам; превосходит SVM/CRNN | статья, код не заявлен | на миксе с известным лидом (соло-гитара, вокал) — точность по секциям; смена лида в соло должна ловиться |
| **PANNs / CLAP-эмбеддинги** | PANNs: https://github.com/qiuqiangkong/audioset_tagging_cnn · CLAP: https://github.com/LAION-AI/CLAP | zero-shot теги ролей по текстовым промптам («kick drum», «rhythm guitar», «accordion»); у нас PANNs уже есть в `describe.py` | PANNs MIT, CLAP MIT | косинус между стемом и промптами ролей; на 20 дорожках — top-1 ≥ 70 % |
| **Имена дорожек** | — | самый дешёвый первый проход: `kick`, `snare`, `hat`, `bass`, `gtr L`, `vox` | — | покрытие: сколько дорожек проекта получили роль без ручной правки |

Практическая схема (совпадает с архитектурой MixAgent, см. 4.4): **имя → эмбеддинг →
активность → ручной override**. Итог: `{stem: (role, confidence, evidence)}`, где evidence —
«имя совпало», «CLAP top-1», «OpenMIC активность 0.8», «лид по Lead-Detection».

Важно: роль — не инструмент. Один стем может быть «keys» (баян + пэд), одна роль может
состоять из 5 дорожек (барабаны). Поэтому роль — это **шина**, и все дальнейшие метрики
считаются по шине, а внутри шины — по желанию (Shapley по компонентам).

### 4.2 Слышимость роли (partial loudness)

Метод — тот же, что в разделе 3.1, но цель не стем, а шина роли:

```
E_role(f) = Σ_{m ∈ role} E_m(f)
N_p,role = N(E_role + E_rest) − N(E_rest)
A_role(z) = N′_p,role(z) / N′_solo,role(z)
```

Дальше — вектор по 7 областям (sub…air), а не одно число: именно вектор говорит,
фейдер это или EQ (раздел 11.2). Глобальная `A_role` — только для ранжирования ролей.

Проверка: синтетика из известных шин; убрать роль целиком → её `A → 0`, у остальных `A`
растёт; добавить роль → падает у тех, с кем перекрывается по полосам. Направление должно
совпадать всегда, величина — в пределах 10 %.

Что есть из многодорожечных датасетов:

| **The Mix Evaluation Dataset** | https://www.dafx.de/paper-archive/2017/papers/DAFx17_paper_49.pdf | миксы, собранные в реальных условиях, с метаданными | по статье | оценка «похоже на профессиональный микс» |

Чего в них **нет**: ни один не содержит **целей баланса по ролям**. Их надо посчитать
самим — это и есть вклад нашего корпуса. Жанровые метки тоже неоднородны: у Slakh жанра
нет (синтетика), у MUSDB18 он в tracklist, у MedleyDB — в метаданных; для остального
нужен классификатор или ручная разметка.

Процедура:

1. Для каждого трека корпуса — роли (4.1) и вектор `A_role` по 7 областям (4.2).
2. Нормировка (4.5), чтобы числа не зависели от мастера и аранжировки.
3. По жанру: медиана и робастная ковариация (shrinkage, т.к. треков мало).
4. Для нового проекта: расстояние Махаланобиса до медианы жанра, перцентиль; ближайшие
   k соседей — для объяснения «вот эти треки звучат так же».
5. Совет: `Δg = clamp((A_target − A_mine)/s, ±3 дБ)` по каждой роли, где `s` измерена.

Проверка: leave-one-track-out — ближайший жанр должен угадываться лучше случайного
(AUC ≥ 0.8 на 5–6 жанрах); совет на отложенном треке — `median|Δg| < 1.5 дБ`.

### 4.5 Нормировка: чтобы числа были сравнимы между проектами

Три независимые оси, которые нельзя смешивать:

1. **Уровень прослушивания.** Все замеры — при 75 дБ SPL, одной калибровкой по миксу.
   При 70/75/80 дБ `N_mix` меняется в разы, доли — на ~1 п.п.; фиксировать и писать в JSON.
2. **Мастер-гейн.** `A = N_partial/N_solo` инвариантна к общему усилению по построению —
   это её главное преимущество перед LUFS. Проверка: тот же микс с −6/+6 дБ → `|ΔA| < 0.01`.
3. **Аранжировка.** Слышимость роли зависит от того, что ещё играет. Поэтому сравнивать
   только внутри страт: одинаковый набор активных ролей, близкая плотность (onsets/с),
   близкий спектральный центроид. Иначе «other 75 %» — артефакт того, что в один стем
   свалили полмикса.

Про уровень есть отдельная работа: Fazenda, *Navigating the Mix-Space*
(https://salford-repository.worktribe.com/OutputFile/1495237) — переход из «gain-space»
в «mix-space» и эксперимент, где разные инженеры приходят к согласованным усилениям,
несмотря на разные стартовые точки. Это и есть эмпирическая опора для «цель существует»;
но она про громкость, не про слышимость и не про жанр.

### 4.6 Как проверять жанровую модель

1. **Роли:** confusion matrix на 30–50 вручную размеченных дорожках; стабильность роли
   по трём окнам одного трека ≥95 %.
2. **Слышимость:** синтетика (убрать/добавить роль) — направление 100 %, величина ±10 %.
3. **Жанр:** leave-one-track-out; AUC ≥0.8; совет на отложенном треке `median|Δg| < 1.5 дБ`.
4. **Инвариантность:** мастер ±6 дБ → `|ΔA| < 0.01`; смена секции той же фактуры → `|ΔA| < 0.05`.
5. **Замкнутый цикл:** применить совет → перемер → `verify()`: цель приблизилась,
   ни одна другая роль не ушла дальше deadband. Иначе — откат.
6. **Слепой тест:** 10 пар A/B, инженер выбирает наш вариант ≥60 % — иначе модель
   оптимизирует не то.

### 4.7 Чего в литературе НЕ решено (честный список)

1. **Нет стандартной таксономии ролей.** Slakh — 34 класса, OpenMIC — 20 инструментов,
   MedleyDB — инструменты, MoisesDB — стемы; сопоставление между ними ручное.
2. **Нет корпуса «профессиональные миксы + стемы + роли + жанр» в одном месте.**
   Mix Evaluation Dataset мал, MUSDB18 — 4 стема, Slakh — синтетика.
3. **Нет жанровых нормативов баланса, подтверждённых статистикой.** Книги дают эвристики,
   а *Mixing Techniques for Audio* прямо говорит: правила не переносятся между жанрами.
4. **Объективные меры маскировки плохо предсказывают воспринимаемую** (Hafezi & Reiss 2015) —
   значит, любая «цель» требует слуховой валидации.
5. **Partial loudness нет в открытом Python** (раздел 2): AMT — MATLAB/GPL, deeuu — C/GPL.
6. **Модель не знает панорамы.** Ward 2012 и Ford 2015 вводят spatial release отдельно;
   в реальном миксе панорама — половина разборчивости, у нас её нет.
7. **Жанр — не скаляр.** Поджанры, эпоха продакшна, лейбл-стиль; ошибка классификатора
   течёт в цели, а оценить её нечем.
8. **Аранжировка — конфаундер.** Слышимость роли зависит от плотности; без стратификации
   «цели» смещены (наш пример: `other` 75 % — артефакт таксономии, а не «гитары громче всех»).
9. **Перенос стиля не объясняет.** Diff-MST и Koo дают аудио/параметры, но не «почему
   и на сколько»; интерпретируемость — открытая задача.
10. **Автокоррекция «на слух» не работает.** MixAgent прямо пишет: мультимодальные модели
    при попытке слушать и править часто **ухудшают** микс; надёжная коррекция — открытый вопрос.
11. **Лицензии.** MUSDB18/MedleyDB/MoisesDB — NC/SA; коммерческое использование корпуса
    ограничено, а Slakh хотя и CC BY, но синтетический.
12. **Нет эталона для оценки самой «жанровой модели».** Метрика требует валидации на
    слушателях, а её ещё никто не построил.

### 4.8 Что это значит для flctrl

Добавить два модуля к плану из раздела 11:

```python
# flctrl/roles.py
def assign_roles(paths: dict[str, str], *, hints: dict | None = None) -> dict
    """{stem: {"role": "kick"|"snare"|"hats"|"bass"|"gtr_rhythm"|"gtr_lead"|
               "keys"|"vocals", "confidence": 0..1, "evidence": [...]}}"""

def role_buses(paths, roles) -> dict[str, list[str]]

# flctrl/genre.py
def fit(corpus_dir, *, genre_key="genre", level_spl=75.0) -> dict   # медиана + ковариация
def nearest(vector, model) -> dict        # расстояние, перцентиль, k соседей
def advise_role(vector, model, *, max_db=3.0) -> list[dict]
```

Порядок работ: роли (1 день) → шины и `A_role` (0.5) → корпус и распределение (1) →
`nearest`/`advise` (1) → замкнутый цикл (0.5). Приёмка — 4.6.

Главное ограничение, которое надо принять заранее: **жанровая модель — это не «правильный
баланс», а «типичный для корпуса»**. Она отвечает «на сколько мы отличаемся от медианы
жанра», а не «как правильно». Поэтому в ответе всегда должны ехать перцентиль и IQR,
а последнее слово — за проверкой на слух.

## 8. Метрики эффектов

### 8.1 `blind_rt60` — слепая оценка времени реверберации

- **Ссылка:** https://github.com/nuniz/blind_rt60
- **Что реализует:** RT60 по Ratnam et al. (2003), оценка по затуханиям в скользящем окне,
  визуализация гистограммы оценок.
- **Лицензия:** MIT. `pip install blind_rt60`.
- **Входы:** сигнал + fs (речь/музыка), параметры окна.
- **Применимость:** метрика «хвоста» для стема/шины: RT60 до и после реверба и против
  референсного стема. На плотной музыке — с осторожностью.
- **Как проверить:** синтезировать IR с известным T60 через `pyroomacoustics` — оценка
  в пределах ±10 %.

### 8.2 `pyroomacoustics`

- **Ссылка:** https://github.com/LCAV/pyroomacoustics
- **Что реализует:** симуляция комнат, RIR, геометрия, beamforming; эталон для проверки
  метрик хвоста.
- **Лицензия:** MIT. `pip install pyroomacoustics`.
- **Применимость:** только тесты (синтетические IR с известным T60).
- **Как проверить:** n/a (эталон).

### 8.3 `librosa` — плотность событий

- **Ссылка:** https://github.com/librosa/librosa
- **Что реализует:** onset detection, spectral flux, beat tracking, STFT/CQT.
- **Лицензия:** ISC. `pip install librosa` (тянет numba/llvmlite).
- **Входы:** сигнал + fs; hop/n_fft.
- **Применимость:** «плотность» = onsets/с; сравнение стема с референсным стемом той же группы.
- **Как проверить:** клик-трек 120 BPM → 2.0 события/с (±5 %).

### 8.4 `auraloss` — LSD и MRSTFT

- **Ссылка:** https://github.com/csteinmetz1/auraloss
- **Что реализует:** `MultiResolutionSTFTLoss`, `STFTLoss`, mel-варианты, SI-SDR;
  перцептивное взвешивание mel.
- **Лицензия:** Apache-2.0. `pip install auraloss`.
- **Входы:** тензоры `(batch, ch, samples)`.
- **Применимость:** «одно число похожести тембра» для стема против референса; для отчёта и
  ранжирования. Не объясняет, что крутить.
- **Как проверить:** одинаковые сигналы → 0; +3 дБ → постоянный сдвиг, не ноль; узкий срез
  1 кГц → локальный рост.

### 8.5 Нелинейные искажения (THD) — `scipy`/`numpy`

- **Ссылка:** пакета нет, ~20 строк: синус 1 кГц → цепочка → FFT → сумма гармоник 2–5.
- **Что реализует:** THD+N, «сколько гармоник добавила цепочка».
- **Лицензия:** BSD-3 (scipy).
- **Применимость:** проверка сатурации/клиппера в `sandbox.py`; на музыкальном материале не
  измерить (реверб/дилей дают остаток, неотличимый от искажений).
- **Как проверить:** байпас → −∞ дБ; известный мягкий клип → сравнить с аналитикой.

### 8.6 ECMA-418-2 (модуляция) — `phonometry` / `sottek-hearing-model`

- roughness (asper), tonality (tu), fluctuation (vacil) — «грязь», «звон», «каша».
- **Применимость:** характеристика эффектов (сатурация ↑ roughness, реверб ↑ fluctuation),
  сравнение с референсным стемом.
- **Как проверить:** синус + AM 70 Гц → roughness растёт; чистый синус → ≈0.

### 11.2 Правила

1. `max|d_r| < deadband` → не трогать.
2. Дефицит плоский (`std/|mean| < 0.6`, один знак) → фейдер, `Δg = clamp(mean(d)/s, ±3 дБ)`.
3. Дефицит локализован → EQ по областям, `ΔL = clamp(d_r/s_r, ±4 дБ)`, соседние области — в полку.
4. Область занята маскером → сначала попробовать срез маскера на 2 дБ и сравнить прирост.
5. Один ход → перемер → `verify()` → следующий. Никогда не применять весь список сразу.

### 11.3 Куда встраивать

- `listen_layer.py` — CLI-команда `attribute`.
- `fl_lib.Hear.attribute()` — через `_hear_cli` (phonometry только в Py3.13).
- `flctrl_mcp/server.py` — `fl_attribute`, `fl_advise`, `fl_verify`.
- `judge.NOISE` — добавить `audib: 0.02`, `share_pct: 1.5`, `region_A: 0.05`.

### 11.4 Приёмочные тесты

1. **Синтетика, известный ответ:** микс из 4 стемов, +6 дБ одному → совет `+6 ± 0.7 дБ`,
   `kind="fader"`; срез 3 дБ на 3 кГц → `kind="eq"`, область `pres`, знак минус.
2. **Leave-one-out по корпусу:** цели по 5 трекам → совет шестому; `median|Δg| < 1.5 дБ`,
   направление верное в ≥5/6.
3. **Повторяемость:** два прогона побитово равны; соседние секции одной фактуры → `|ΔA| < 0.05`.
4. **Сверка с эталоном:** один стем через AMT `moore1997` и через наш код — `N_partial`
   в пределах 5 %.
5. **Согласованность с человеком:** на vers1 модель должна независимо находить провал
   железа (pres/air) — известная проблема, найденная вручную.

## 12. Риски, которые видны из источников

1. **Готового partial loudness нет** — свой код надо сверить с AMT, иначе можно годами
   считать «свою» модель.
2. **Модель MG не знает панорамы.** Ward 2012 и Ford 2015 признают spatial release from
   masking; без него разведённый источник выглядит более замаскированным, чем есть.
3. **Объективные меры маскировки плохо предсказывают воспринимаемую** (прямая оговорка
   Hafezi & Reiss 2015) — обязательна проверка на слух или на корпусе.
4. **SII на металле насыщается** (наш результат 0.000–0.093) — не строить вывод на нём.
5. **Demucs-таксономия:** 4 стема сваливают гитары/баян в `other`; лечится `htdemucs_6s`.
6. **Лицензии:** `matchering`, `pedalboard`, `sottek-hearing-model`, `deeuu/loudness` — GPL-3.0.
   Если flctrl распространяется не под GPL, эти зависимости нельзя тащить в поставку.
7. **`phonometry` требует Python 3.13** и отсутствует в основном процессе MCP — только
   подпроцессом (как сейчас `masking`/`psycho`).
8. **Корпус из 6 треков** — коридор, а не истина; расширять Mix Evaluation Dataset.
9. **ML-авто-микс** (FxNorm) даёт готовый микс без объяснения; как ядро не подходит.
10. **Жанровая модель** — отдельный список из 12 нерешённых пунктов в разделе 4.7;
    коротко: нет таксономии ролей, нет корпуса «миксы + стемы + роли + жанр», нет
    жанровых нормативов, а аранжировка и панорама искажают слышимость.

## Приложение B. Формулы, на которые опирается план

**Возбуждение и удельная громкость (Glasberg & Moore 1990; MG 1997; ISO 532-2):**

```
ERB(f) = 24.7 · (4.37·f/1000 + 1)                      # Гц
roex(p): W(g) = (1 + p·g)·exp(−p·g),  g = |f − f_i| / f_i
p = 4·f_i / ERB(f_i)                                   # с поправкой на уровень
E(f_j) = Σ_i W(|f_j − f_i|) · 10^(L_i/10)              # сумма мощностей
N′(z) = C · [(E(z)/E_thr(z))^0.23 − 1],  E > E_thr     # C ≈ 0.046871
N = ∫ N′(z) dz                                         # сон
```

**Частичная громкость и аудибельность (Ward 2012, cross-adaptive):**

```
E_b(f) = Σ_{m ≠ t} E_m(f)
N′_p,t(z) = max(0, N′(E_t(z) + E_b(z)) − N′(E_b(z)))
N_p,t = ∫ N′_p,t(z) dz
A_t(z) = N′_p,t(z) / N′_solo,t(z)                      # 0..1
```

**Цели и перевод в дБ:**

```
d_r = A_mine(r) − A_ref(r)                             # дефицит по области
s   = ΔA/Δg при +1 дБ на стем                          # измерять, не предполагать
Δg  = clamp(mean(d)/s, ±3 дБ)                          # фейдер
ΔL_r = clamp(d_r/s_r, ±4 дБ)                           # EQ по области
```

**Разборчивость:**

```
SII = Σ_i I_i · A_i,   A_i = clip((E_i − D_i)/(U_i − D_i), 0, 1)   # ANSI S3.5, 18 полос
STOI = mean_{i,frame} corr(x̂_i, ŷ_i)                                # 1/3-окт., 256 мс
```

**Тембр и хвост:**

```
LSD = sqrt(mean_k (20log10|X_k| − 20log10|Y_k|)²)
MRSTFT = Σ_m ( ||log|X_m| − log|Ŷ_m|||₁/N + || |X_m| − |Ŷ_m| ||_F / || |X_m| ||_F )
EDC(t) = 10log10( ∫_t^∞ h²(τ)dτ / ∫_0^∞ h²(τ)dτ )      # Шрёдер; T20/T30 по −5..−25/−35 дБ
```

**Нелинейность:**

```
THD = 20log10( sqrt(Σ_{k=2..5} A_k²) / A_1 )           # синус 1 кГц через цепочку
```
