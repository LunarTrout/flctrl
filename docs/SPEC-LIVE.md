# SPEC-LIVE: доступ к живому FL без гонки

Домен LIVE — единственный, где есть общий ресурс: один живой экземпляр FL.
Задача спеки: сделать так, чтобы этот ресурс никогда не стал причиной гонки,
и чтобы чтение вообще не требовало координации.

## 1. Три класса доступа

| класс | что делает | координация | кто пользуется |
|---|---|---|---|
| **passive read** (tap) | читает память процесса: позиция, темп, буферы, метры, структура | не нужна | замеры, контекст, запись |
| **control write** | меняет значения: громкость, панорама, параметры, слоты, транспорт | очередь у владельца | правки, планы |
| **exclusive lease** | операции, несовместимые с живым проектом: рендер, смена проекта, перезапуск | аренда | рендер, тесты, сброс |

Ключевое: **чтение пассивно**. Оно не шлёт команд, не меняет состояние и не
мешает FL. Поэтому блокировать чтение нечем и не нужно.

## 2. Tap: один читатель, много потребителей

- Один процесс (`tap`) прикрепляется к FL через Frida и держит сессию.
- Читает по слоям: позиция/темп/транспорт (10–100 Гц), буферы дорожек
  (поблочно), структура (по изменению), метры (по запросу).
- Публикует: `memmap` для чисел и кольцевой буфер для аудио; либо локальный
  сокет для событий.
- Потребители (анализ, MCP, запись) читают опубликованное и к FL не обращаются.
- Если tap отвалился — потребители видят `stale` с временем последней публикации,
  а не висят.

Ограничение: на процесс — одна сессия Frida. Второй читатель подключается к
tap, а не к FL.

## 3. Control: очередь и версия

Все изменения идут через владельца, по одному:

```
validate(path, value) → apply → read back → bump(project_version) → ответ
```

- запись редкая, поэтому очередь тривиальна (FIFO, без приоритетов);
- каждая правка возвращает `before/after` и новую `project_version`;
- пачка применяется атомарно: при ошибке откат всех элементов;
- отказ структурный: `code`, `path`, границы. Без «что делать дальше».

## 4. Exclusive lease

Аренда берётся только там, где живой проект мешает:

- рендер (`render`) — требует закрытой FL;
- смена проекта (`project.open`);
- перезапуск (`system.restart`).

Правила: одна аренда на всех, `lease_id`, TTL, освобождение при выходе процесса.
Пока аренда жива: `control write` и `tap` получают `busy` с оставшимся временем.

Запись дорожек аренды **не требует**, если идёт из tap: это пассивное чтение.

## 5. Версии и устаревание

- `project_version` растёт на каждой записи;
- `tap_seq` растёт на каждой публикации;
- кадр замера хранит обе: по ним видно, снят ли он до правки;
- сравнение кадров разных версий разрешено, но помечается `stale: true`;
- применять план, построенный на устаревших данных, нельзя — это проверяется
  при применении, а не на словах.

## 6. Отказы и восстановление

| ситуация | что видит клиент | что делает система |
|---|---|---|
| FL не запущена | `fl_not_running` | ничего, ждёт |
| мост молчит | `bridge_dead` + подсказка по MIDI | перезапуск скрипта |
| UI FL завис | `fl_hung` | `reset` по правилам `reset_fl` |
| tap отвалился | `stale` + время | переподключение |
| аренда истекла | `lease_expired` | освобождение, работа продолжается |
| очередь переполнена | `busy` | отказ, без потери чужих команд |

## 7. Что проверять тестами

1. **Пассивность чтения**: 10 минут чтения метра — FL не меняет состояние,
   загрузка CPU в пределах, ни одной записи в проект.
2. **Отсутствие гонки записи**: 100 параллельных `set` из разных процессов дают
   последовательное применение и корректную версию.
3. **Аренда**: во время рендера `set` не проходит, после — проходит.
4. **Устаревание**: план, снятый до правки, отвергается.
5. **Восстановление**: убитый tap → `stale`, поднятый tap → свежие данные.

## 8. Чего спека не делает

- Не требует «сначала прочитать, потом писать» — порядок свободный.
- Не вводит сессий и состояний, которые что-то блокируют.
- Не претендует на многопоточность внутри FL: FL однопоточен по UI, и это
  принимается как факт.
