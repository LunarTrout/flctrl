# Архитектура flctrl: план перестройки

Документ фиксирует, что сейчас мешает, и какой должна стать библиотека, чтобы
ею было удобно и надёжно решать наши задачи — и чтобы она оставалась
универсальной, а не «под один трек».

## 1. Что показал аудит

**Две копии библиотеки.** В репозитории `flstudio-lib/flctrl` — 35 модулей,
это канон (свежий: 1334 строки в `fl_lib.py`). В рабочей папке
`flstudio-mcp/tools-local` лежат **27 модулей с теми же именами**, из них
`fl_lib.py` разошёлся на 435 строк, `hear_cli.py` — на 72. Любая правка
рискует уйти не в тот файл, и уже уходила.

**237 одноразовых скриптов** в `tools-local`. Половина — это то, что должно
быть методами библиотеки (`_body.py`, `_vox_fix.py`, `_drums_clean.py`…).

**Два окружения.** Живое управление живёт в 3.12, слух — в 3.13, потому что
`phonometry` есть только там. Мост через подпроцесс работает, но размазан по
коду: каждый метод сам решает, куда идти.

**Несогласованный API.** `measure(path, a, b)` принимает границы позиционно,
`masking(stems, mix_path)` — обязательный микс, `attribute` — словарь стемов.
Один и тот же смысл «отрезок» задаётся тремя способами.

**Нет объекта сессии.** Каждый вызов самостоятелен: состояние проекта,
выбранная секция, история правок и откат живут в голове вызывающего.

**Слой решений почти пуст.** Есть `judge` (принять/отклонить два замера) и
`predict` (линейное предсказание), но нет того, что превращает расхождение
с целями в конкретный план правок.

## 2. Целевая структура

Один пакет, слои снизу вверх; каждый слой знает только про нижний.

```
flctrl/
  core/            доступ к FL и жизнь проекта
    link.py        мост, порт, health, авто-подъём
    state.py       дорожки, каналы, плагины, маршруты, плейлист
    act.py         запись параметров, громкости, панорамы, маршрутов
    create.py      рендер, живая вставка, дорожки, перезагрузка
    safe.py        снапшот, откат, бэкапы
  ear/             измерение. Чистые функции, без FL
    bands.py       полосы, калибровка, спектры
    loudness.py    N, N'(z), резкость, LUFS, crest
    partial.py     LOO, слышимость A, чувствительность dN/dB
    masking.py     матрица маскировки, unmask
    psycho.py      шероховатость, тональность
    sections.py    автосекции, активные окна
    stereo.py      корреляция, ширина, потеря в моно
  model/           корпус и цели. JSON внутрь и наружу
    roles.py       роли инструментов
    targets.py     распределения по ролям и осям
    balance.py     вектор проекта, solve с капом, check
    objective.py   расстояние до целей, худшие места
  decide/          правила
    advice.py      расхождение → конкретные правки (gain / EQ / pan)
    verify.py      приёмка: значимость, цель, ущерб
    journal.py     журнал решений и результатов
  session.py       MixSession: проект, секция, история, откат
  recipes/         жанровые профили как данные (black_metal.json, rock.json)
  mcp/server.py    поверхность для моделей
```

**Принципы, которые решают текущие проблемы.**

1. **Один канон.** Код живёт только в репозитории. `tools-local` — для
   экспериментов, и в нём запрещены файлы с именами модулей библиотеки.
2. **Слои не текут.** `ear` не знает про FL; `model` не знает про подпроцессы;
   `decide` не пишет в FL; `core` не считает звук.
3. **Один переходник окружений.** Всё, что требует `phonometry`, вызывается
   только через `ear/interp.py`. Остальной код работает в любом Python 3.10+.
4. **Единый способ задавать отрезок.** Везде `section=(a, b)` — один объект,
   `None` значит «весь файл». Никаких позиционных пар.
5. **Всё, что считается, возвращает словарь с числами и единицами**, а не
   голый массив: результат должен быть пригоден для журнала и MCP.
6. **Универсальность через роли и корпус.** Проект описывается ролями;
   жанр — файлом-рецептом; ничего не зашито под конкретный трек.

## 3. MixSession — то, чего сейчас нет

```python
s = fl.session.open("song.flp")        # или живой проект
s.section = (120, 150)                 # рабочее окно
s.baseline()                           # замер «до», снапшот
plan = s.plan(refs="black_metal")      # цели корпуса → правки
s.apply(plan[0])                       # одна правка
v = s.verify()                         # accept / reject / мало данных
s.log                                  # история: что, почему, что вышло
s.rollback()                           # откат последней правки
```

Правила сессии, без которых она опасна:
одна правка за шаг; снапшот перед первой; автоматический откат при `reject`;
запись в журнал каждого шага; запрет закрывать чужой проект (уже есть в `safe`).

## 4. Переход (по шагам, каждый с проверкой)

| шаг | что делаем | как проверить |
|---|---|---|
| 1 | Заморозить `tools-local`: удалить копии модулей библиотеки, оставить только скрипты | `comm -12` по именам даёт пусто |
| 2 | Вынести измерение в `ear/` с единым `section=` | дымовые тесты 17/17, `measure`/`bands`/`masking` дают те же числа на тех же файлах |
| 3 | Вынести корпус и цели в `model/` | `balance.build` на корпусе даёт те же медианы, что `partial_corpus.json` |
| 4 | Добавить `decide/advice.py` | на синтетике: +3 дБ дефицита → совет +3±0.7; срез 3 кГц → совет в pres, не фейдер |
| 5 | Ввести `session.py` | сценарий «правка → замер → accept/reject → откат» проходит на `small.flp` |
| 6 | Перевести MCP на новые слои, оставив старые имена | `--selftest` показывает то же число инструментов |

## 5. Чего этот план НЕ делает

- Не обещает «идеальный микс по кнопке»: цели — распределение корпуса, и
  последнее слово всё равно за слушателем.
- Не тащит обученные модели: у нас нет датасета, а black-box по реальному
  рендеру даёт проверяемый результат без обучения.
- Не ломает обратную совместимость: старые имена методов остаются
  обёртками, пока новые не покроют их полностью.
