# SPEC: полный контекст проекта и всего, чего не хватает

Связка принципов и модель целиком — `docs/DESIGN.md`; здесь только пробелы.

Документ отвечает на один вопрос: **что нужно знать и уметь, чтобы свести трек
идеально — с пониманием всех нюансов — и чего у нас для этого ещё нет.**

Формулировка требования в четырёх глаголах:

> по любой дорожке в любой момент времени **знать состав** (клипы, ноты, хвосты,
> локальное время источника), **знать обработку** (плагины, автоматизация),
> **знать восприятие** (частичная громкость, маскировка, транзиент, стерео)
> и **уметь менять** с предсказуемым результатом и проверкой числом.

**Главное — записать.** Всё остальное либо считается из записи, либо уже есть.
Оценка «насколько далеко от жанра» не требует новых слоёв: она уже работает по
файлам (`audit`/фронты, `snrtargets`, `wall`, `transients`, `harmony`). Как
только появятся файлы дорожек, те же метрики применятся к ним напрямую.
Поэтому запись потока и точное время — единственный настоящий блокер.

## 1. Разрешение по времени

| Слой | Шаг | Что считается | Где живёт |
|---|---|---|---|
| блок движка | 512 сэмплов ≈ 10.7 мс (48 кГц) | RMS, пик, ERB-полосы, транзиент, ширина | в агенте, не пишется |
| матрица контекста | 50 мс (20 строк/с) | агрегаты по дорожкам и полосам | memmap, кольцо + сворачивание |
| события | блок за блоком вокруг атаки | форма удара, клиппинг, дакинг | только на событиях |
| секции/клипы | такт/клип | медианы, min/max, сравнение с корпусом | маленькая таблица |

20 строк/с достаточно для «обстановки», но **не** для транзиентов: атака бочки
5–15 мс при шаге 50 мс размазывается. Поэтому блоковый слой обязателен.

## 2. Кадр контекста (целевая схема)

```
frame = {
  sample_pos, seconds, tempo_bpm, time_sig, bar_beat, loop,
  tempo_map_id,
  tracks: [{
     mixer, role?, level:{rms,peak,true_peak}, bands_erb[24..30],
     width, correlation, transient:bool,
     sources: [{kind:"audio"|"midi", clip_id, source_offset_s,
                gain_db, fade, muted, pattern_id?, notes?}],
     tails: [{from_clip, rt60, level_db}],
     plugins: [{slot, name, params_digest, meters:{gr_db, level_db}}]
  }]
}
```

Источники у дорожки — **список**, а не один: на одной дорожке может звучать
несколько клипов, а реверб звучит после конца клипа (хвост — тоже источник).

## 2.5. Куб: одна форма для всех картин

Все данные — и матрица из потока, и замеры по файлам, и референсы — ложатся в
одно хранилище с фиксированными осями:

```
оси: время (сэмпл → такт) × дорожка (→ роль) × полоса (ERB) × метрика
```

Матрица из потока — срез `rms[время, дорожка, полоса]`. Спектр файла — тот же
срез, посчитанный иначе. Референс — такой же куб, другой источник. Сравнение
поэтому всегда выровнено по построению.

**Картина = проекция куба**, а не отдельный инструмент:

```
картина(metric="rms", by=["track"], where={section:"припев"})
картина(metric="partial", by=["role"], where={bar:[17,24]})
```

**Провал вниз бесплатный:** у каждой клетки есть провенанс — источники (клипы,
ноты, хвосты), обработка (слоты, параметры), сырой отрезок записи.

### Гранулярность: у референсов нет 32 дорожек

Это уже решено, и правило надо сохранить в кубе:

1. `roles.py` приводит любой проект к ролям `drums / bass / guitar / keys /
   vocals / other` — по именам и по измерениям.
2. Референсы разделяются на 4 стема, то есть существуют только на уровне ролей.
3. Сравнение идёт на **самой грубой общей гранулярности**: референс ↔ мы — по
   ролям; наш «до/после» — по дорожкам.
4. Метрика выбирается инвариантной: не «громкость дорожки», а отношение
   «роль / остальное» (`SNR`), не зависящее от числа дорожек и от уровня.
5. Аддитивные метрики (rms, peak) внутри роли **суммируются**; неаддитивные
   (частичная громкость, маскировка) считаются как «роль против остального».
6. Отсутствие данных — **явный пропуск** в таблице, никогда не ноль.

Поэтому в кубе ось «дорожка» имеет атрибут `role`, а проекция `role` — это
законный, более грубый вид той же картины.

### Обход разделения: обратная задача (основной путь)

Разделение референса не нужно. Это уже проверено и реализовано в `invmix.py`:

- у референса берётся цель **на уровне микса** — семь областей, резкость,
  крест, стерео;
- у нас есть **настоящие стемы** — дорожки проекта;
- неизвестные — гейны ролей; сумма стемов с гейнами даёт те же метрики, и
  расстояние до цели минимизируется;
- уравнений больше, чем неизвестных, ответ проверяем: сумма должна попасть в
  целевой вектор.

Отсюда важное следствие: **цели по ролям — побочный продукт решения**, а не
измерение на стемах. Формулировка «вот такие гейны дают совпадение с корпусом»
и есть цель по ролям.

Поэтому порядок такой: `референс → цели микса → обратная задача на наших
дорожках`. Стемы референса — только перекрёстная проверка, с метрикой качества.
`docs/snr_baseline.json`, посчитанный из стемов, подлежит замене на цели,
полученные решением (или помечается как приблизительный).

### Качество разделения референсов

Разделение на стемы — слабое звено: у нас 6 референсов и «микро-модель», качество
которой никто не проверял. Поэтому правило: **никакие цели не строятся на стемах
без проверки качества.**

1. **Референсы дают только инвариантное** — то, для чего разделение не нужно:
   полный микс, спектральный баланс, крест/динамика, транзиенты, стерео-ширина,
   «стена» и провалы, секции, гармония и строй, темп и плотность.
2. **Роли из стемов — только как грубая доля**, с числом уверенности. Проверки:
   ошибка реконструкции (`сумма стемов` против микса) и протечка (энергия стема
   в полосах, где его быть не должно).
3. **Цели по ролям берутся из проекта и литературы**, а не из стемов: в своём
   проекте роли настоящие (после появления записи дорожек), стемы — только там,
   где уверенность высокая.
4. **Разделять один раз и хорошей моделью** (`htdemucs_ft`, Bandit): шесть
   треков, спешки нет, это офлайн-прогон. Версия модели и метрика качества
   сохраняются вместе с результатом.
5. **В целях хранить провенанс**: `source = full_mix | stems(<модель>, recon_err) |
   own_tracks`. Видно, каким целям верить, а какие приблизительные.

## 5. Блокеры и неизвестное

1. **VST в слот вживую** — резолвер видит только `Plugins\Fruity`; `.fst`, `.dll`,
   прямой загрузчик и `uiInsert` не сработали.
2. **Рендер при открытом проекте** — CLI требует закрытой FL.
3. **Создание каналов рэка** — в API отсутствует.
4. **`automateEvent`** — идентификаторы событий неизвестны.
5. **Split-экспорт** — `render_job` умеет принимать результат, но включение
   настройки в проекте не автоматизировано.
6. **Память** — все смещения привязаны к FL 25.2.5 build 5319; после обновления
   нужна перепроверка (см. I4).

## 6. Порядок работ

1. **A1 + A5 + A6** — поток аудио с дорожек (в стерео) и **запись его на диск**.
   Это единственный блокер: без записи всё остальное — оценки по файлам.
2. **B1 + B2** — точная позиция в сэмплах и точный темп, чтобы записанное
   склеивалось с картой клипов и тактами.
3. **C1 + C2 + C6** — провенанс: карта есть, добавить смещение в сэмпле и
   отметку свежести; карта должна соответствовать тому, что в проекте сейчас.
4. **C3** — ноты из паттернов (MIDI-часть картины).
5. **A7 + A3** — хвосты и мастер: «что звучит сейчас» и проверка суммы.
6. **G1 + G5 + G7** — частичная громкость, транзиенты и маскировка **по
   записанным дорожкам**; новой математики не нужно, только применить файловые
   метрики к записи.
7. **D3 + E2** — метры плагинов и запись автоматизации.
8. Остальное — по мере надобности.

## 7. Критерий готовности

Первый рубеж — **запись**: любой участок любой дорожки пишется в файл без
рендера проекта и без соло-проходов, с точной позицией и темпом.

Полная система отвечает числами из записи и памяти, без рендера:

- «что звучит на этой дорожке в этот момент и откуда именно» — состав и локальное время;
- «насколько этот инструмент слышен в миксе» — частичная громкость;
- «кто его маскирует и в какой полосе» — матрица маскировки;
- «что делает плагин» — метры и параметры;
- «насколько это отличается от жанра» — сравнение с корпусом по секциям;
- «что будет, если я изменю вот это» — предсказание и проверка после.
