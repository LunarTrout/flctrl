# Как это работает

Документ для того, кто будет читать код. Здесь устройство каждого слоя:
что он измеряет, на чём основан, где врёт и что проверено запуском.

---

## 1. Общая картина

FL Studio не даёт публичного API. Всё, что делает пользователь руками —
вставка плагина, создание канала, правка ручек — не имеет вызова, к которому
можно обратиться из кода. При этом сводить вслепую невозможно: решения
принимаются по тому, что слышно, а «слышно» до недавнего времени не было
измеримо.

Библиотека закрывает это тремя независимыми каналами доступа:

| Канал | Что даёт | Ограничение |
|---|---|---|
| **Файл `.flp`** | читать всё, что сохранено: дорожки, каналы, плагины, плейлист, клипы с путями, автоматизацию, темп | только сохранённое состояние |
| **Мост контроллера** | живое управление: любая ручка плагина, громкость, панорама, mute/solo, маршруты, транспорт, ноты | не создаёт объекты |
| **Frida** | создание объектов вживую: вставка, удаление, замена плагина | пока только плагины |

Смысл разделения: файл — источник правды о структуре проекта, мост — руки,
Frida — то, чего нет ни там, ни там.

Сверху лежит слой слуха: он превращает звук в числа, по которым можно
принимать решения и проверять их.

## 2. Слой слуха (`listen_layer.py`, `perceptual.py`)

### 2.1. Громкость

ISO 532-1 через `phonometry`: сначала третьоктавный спектр, затем
специфическая громкость `N′(z)` по **240 полосам Барка**, интеграл — общая
громкость в **сонах**, и параллельно громкость в **фонах**.

Ключевая деталь: соны зависят от точки прослушивания. Замер калибруется на
**90 дБ SPL**, и калибровка считается **по всему треку**, а не по отрезку.
Это не педантизм: при калибровке по каждому отрезку отдельно тишина
«подтягивается» до нормальной громкости, и самый тихий фрагмент
становится «самым плотным». Именно так однажды был получен центр 19.8 с,
LUFS −44 и crest 40.8 — то есть замер тишины вместо музыки.

Проверено: рост на **1 дБ** даёт **+5.1 соны** (81.87 → 86.98). Поэтому соны
сравнимы только при одинаковой громкости, а доли областей — почти нет:
они плывут на **±0.05 п.п.** на 1 дБ.

### 2.2. Резкость

DIN 45692, в **acum**. Считается по специфической громкости с весовой
функцией, подчёркивающей высокие частоты.

Важное свойство, проверенное прямым опытом: резкость **почти инвариантна
к громкости** — те же +1 дБ дают +0.002 acum (1.617 → 1.619). Значит она
измеряет не громкость, а **яркость материала**.

Отсюда правило: резкость нельзя сравнивать между разными по составу
отрезками (внутри одного трека разброс 0.17 acum), но выравнивать её по
громкости не нужно.

### 2.3. Грубость и тональность

ECMA-418-2: `roughness_ecma` (asper) и `tonality_ecma`, оба с разбивкой по
**53 полосам** и по времени (101 × 53). Грубость ловит биения — то, что
в блэк-метале даёт расстроенный строй гитар.

Стоимость: около **45 с на 10 с** материала. Это дорого, поэтому слой
включается точечно, а не в каждом замере.

### 2.4. Разборчивость вокала

STOI против чистого вокала. Работает только на **выровненном** стеме:
сдвиг на 29 мс, который даёт разницу в корреляции с 0.9 до 0.31, стоит
**0.26 STOI** — больше, чем разница между всеми референсами. Поэтому
STMОI считается либо по стему из FL, либо не считается вовсе.

### 2.5. Спектр: 240 полос и семь областей

Профиль по Барку строится по трём осям: уровень, ширина (стерео), модуляция
(насколько полоса «дышит»). Для решений удобнее свёртка в семь областей:

| Область | Барк | Гц | Что это на слух |
|---|---|---|---|
| sub | 0–2 | 0–204 | саб, тело бочки |
| bass | 2–5 | 204–560 | коробка, «картон» |
| lowmid | 5–9 | 560–1278 | тело гитар, грудь вокала |
| mid | 9–14 | 1278–3065 | разборчивость, атака |
| upmid | 14–18 | 3065–6011 | артикуляция, щелчок |
| pres | 18–21 | 6011–9926 | присутствие |
| air | 21–24 | 9926–16374 | воздух |

Названия не совпадают с бытовыми: «bass» здесь — это 204–560 Гц, то есть
**бубнёж, а не низ**. Тело в низкой середине — это lowmid, 560–1278.

### 2.6. Динамика

LUFS (интеграл с гейтом), crest (пик к RMS), LDR — отношение короткого и
длинного окна RMS. LDR считается через кумулятивную сумму: наивный
`np.convolve` с окном 144 000 отсчётов давал квадратичную сложность и 88 с
на 30-секундный отрезок; после замены — **0.53 с**, а весь трек 352 с — **6.6 с**.

### 2.7. Стерео

Корреляция каналов, отношение side/mid в дБ, ширина. Считать их осмысленно
только после того, как устоялся тональный баланс: корреляция берётся по всей
энергии, а 60 % энергии — низ.

### 2.8. Маскировка и разгрузка

`masking` показывает, во сколько дБ и в каких полосах один источник
перекрывает другой. `unmask` — обратная задача: сколько вернётся в дорожке,
если убрать соседа. Это и есть числовое определение «инструменты мешают
друг другу».

Требует валидных стемов. Стемы сепаратора для этого не годятся: гитарный
стем имеет SDR около 3 дБ.

### 2.9. Коридор

Сравнение идёт не с одной цифрой, а с **коридором** из нескольких
референсов, и только на однотипных секциях. Формат:

```python
corridor = {"sharp_mean": {"коридор": [1.40, 1.70]}, ...}
```

## 3. Узнавание и стиль (`describe.py`, `mixstyle.py`)

Два разных вопроса, два разных инструмента.

**`describe`** — эмбеддинги PANNs: «на что это похоже по материалу».
Косинус между нашим миксом и GRIMA — 0.858. Годится для поиска похожих
мест в референсах, не годится для решений о балансе.

**`mixstyle`** — энкодер MIXSTYLE (2048-мерный): «похож ли подход к
сведению» — сжатие, плотность, ширина, характер обработки. Для той же пары
даёт 0.708.

Расхождение чисел — не ошибка, а подтверждение, что метрики меряют разное.
Правило: **`measure` решает, `describe` ищет.**

## 4. Песочница (`sandbox.py`)

Проверка гипотезы без риска: цепочка обработки применяется к отрезку,
настоящими плагинами, и результат меряется тем же слоем слуха.

Примитивы: `gain`, `hpf`, `lpf`, `eq`, `comp`, `sat`, `pan`, `vst3`.
VST3 работают по-настоящему, через `pedalboard`, с реальными файлами
плагинов и реальными параметрами.

Обязательное правило: после правки **выровнять громкость** перед сравнением,
иначе меряется не тембр, а громкость.

---

## 5. Предсказание (`predict.py`)

Аддитивная модель мощности: вклад дорожки складывается с миксом по полосам.
Позволяет ответить «что изменится, если опустить эту дорожку на 2 дБ и
срезать 3 дБ на 300 Гц» без применения.

Честная граница: модель линейна. Всё, что зависит от нелинейности —
компрессия, сатурация, лимитер на мастере — предсказывается плохо.

---

## 6. Приёмка решения (`judge.py`)

Превращает «стало лучше» в проверяемый вердикт: `accept`, `reject`,
`insufficient`.

Как устроено:

1. **Значимость.** У каждой метрики свой порог шума: резкость 0.01 acum,
   соны 0.5, LUFS 0.1 дБ, crest 0.2 дБ. Изменение меньше порога — не
   считается изменением.
2. **Цель.** Направлением (`down` / `up`) или числом.
3. **Побочный ущерб.** Метрика испорчена, если стала **дальше от коридора,
   чем была**. Не «вне коридора», а именно дальше — иначе любая метрика,
   которая уже была вне, блокировала бы всё.
4. **Журнал.** Каждое решение пишется в `_cache/journal.jsonl`.

Тонкость: ущерб считается только для метрик, входящих в коридор. Остальные
могут меняться свободно — иначе система запрещает всё.

## 7. Живое создание объектов (`live_create.py`)

Самая сложная часть. FL не имеет API создания объектов, а отладчики
невозможны: протектор Image-Line убивает процесс за 0.3 с. Работает только
Frida.

### 7.1. Как устроен стенд

1. `safe_fl.frida_spawn()` — закрывает посторонние экземпляры FL, стартует
   `FL64.exe` с тестовым проектом **приостановленным**, под Frida.
2. `Process.attachModuleObserver` — `FLEngine_x64.dll` грузится не сразу,
   поэтому базу модуля ловят в момент загрузки (`getModuleByName` на старте
   падает).
3. После загрузки: `resume`, поиск главного потока, все вызовы — только из
   **UI-потока** (иначе движок не обновляет состояние).
4. Дальше команды идут через `Daemon.run_op` — в том же процессе, без
   сокетов и подпроцессов.

### 7.2. Как находятся слоты

Сканированием памяти по vtable: объект слота опознаётся по указателю на
таблицу методов. У объекта:

| Смещение | Что |
|---|---|
| `+0x160` | номер инсерта (канала микшера) |
| `+0x164` | номер слота (0–9) |
| `+0x64` | состояние: `2` — занят, `-1` (`0xFFFFFFFF`) — пусто |
| `+0x80` | HMODULE загруженного плагина |
| `+0x68` | число параметров |
| `+0x50` | указатель на имя |
| `+0x30`, `+0x38`, `+0x40` | подобъекты (есть только у занятого) |

Фиксированного шага между инсертами **нет**: блоки лежат отдельными
аллокациями. Поэтому адресация через `+0x160/+0x164`, а не арифметикой.

### 7.3. Удаление

Родная функция движка `FLEngine+0xE29570`, `RCX` = объект слота. Делает
полное удаление: снимает с глобального списка, вызывает деструкторы
экземпляра, освобождает подобъекты, `FreeLibrary` для DLL, ставит
`+0x64 = -1`.

Вручную добивать ничего не нужно — и это важно, потому что попытки обнулить
поля напрямую (`+0x30`, `+0x38`, `+0x40`, `+0x50`, `+0x78`, `+0x80`) слот
**не освобождают**: FL продолжает видеть плагин, потому что не тронуто
поле состояния.

### 7.4. Вставка

Родная функция `FLEngine+0xE28E70`, `RCX` = объект слота, `RDX` = путь
строкой. Внутри: подготовка через vtable, проверка файла, загрузка обёртки
`Fruity Wrapper_x64.dll`, `CreatePlugInstance`, заполнение полей и в конце
`[slot+0x64] = 2`.

Строка — **Delphi UnicodeString**, указатель на первые символы, а заголовок
на 12 байт раньше:

```
[-12] u16 CodePage = 1200 (UTF-16LE)
[-10] u16 ElemSize = 2
[ -8] u32 RefCnt
[ -4] u32 Length (в символах)
[  0] UTF-16 символы + NUL
```

Ловушка, на которой был потерян первый прогон: `Memory.alloc` внутри RPC
освобождается после возврата, и к моменту чтения по указателю там мусор.
Слот при этом молча остаётся пустым. Решение — держать буфер в `globalThis`.

### 7.5. Что это доказало

Вставка проверена не только по «FL согласился»: проект сохранялся, файл
вырос с 68 380 до 68 754 байт, после перезапуска плагины на месте. Значит
создание настоящее, а не косметическое.

## 8. Путь через файл

Запасной и полностью рабочий способ создавать плагины, когда живой режим
недоступен.

Запись плагина в `.flp` самодостаточна, поэтому её можно клонировать как
байтовый блок. Структура слота в файле:

```
0xC9 имя → 0xD4 (insert, slot) → 0x9B иконка → 0x80 цвет
        → 0x29 флаг → 0xD5 состояние → 0x62 терминатор
```

Инсерты разделяются событием `0xCC` (имя дорожки микшера). Для любого
установленного плагина есть готовый источник — его `.fst` из базы FL.

Стоимость — перезагрузка проекта около 30 секунд, поэтому вставки собирают
пачкой и перезагружают один раз.

## 10. Где мы врём себе

Перечислено честно, потому что это важнее списка возможностей.

* **Стемы нельзя суммировать**: сумма специфической громкости по стемам
  даёт 1.55× от микса.
* **Гитарный стем сепаратора** непригоден для выводов о балансе (SDR ~3 дБ).
* **STOI без выравнивания** бессмыслен: ошибка синхронизации стоит больше,
  чем разница между референсами.
* **Резкость между разными отрезками** сравнивать нельзя (разброс 0.17 acum).
* **MOS-метрики для речи** (NISQA, SQUIM) к музыке не применять.
* **Предсказание** не учитывает компрессию и сатурацию.
* **Маршруты и темп** живьём ещё не проверялись.
* **Каналы и клипы** создать нельзя — зацепки не найдено.

```bash
../.venv313/Scripts/python.exe tests/test_smoke.py
```

14 проверок файловых слоёв: чтение проекта, замер, полосы, кривая, профиль,
секции, сопоставление, песочница (нулевое усиление и −6 дБ), приёмка,
предсказание. Живые методы пропускаются — им нужен запущенный FL.

Тесты появились после того, как выяснилось: три метода использовались
неправильно (`playlist` возвращает словарь, `clip_files` — список, коридор
имеет вид `{"коридор": [lo, hi]}`). Без тестов эти ошибки жили бы в коде.
